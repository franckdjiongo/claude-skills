§01

Verdict

Ton diagnostic est juste, et le trou est plus large que ce skill. Le rail (server/services/reviews/apply.ts) copie le dossier du skill dans ~/.claude/skills et nulle part ailleurs ; aucune ligne du rail ne mentionne ~/.agents/skills. 17 des 26 skills copiés côté Codex diffèrent de leur source, et 10 portent des chemins cassés comme .Codex/agents/ (37 lignes touchées).

Je recommande l'option B : une seule source dans claude-skills, avec des blocs marqués par runtime, un générateur testé qui produit la variante Codex, et une seconde cible d'installation dans le rail. Copier la même chose aux deux endroits (option A) enverrait à Codex des consignes qu'il ne peut pas suivre (Workflow tool, model:'sonnet', SendMessage).

Pour les modèles : pas de nom daté dans le skill. Il lit un fichier de routage (projet, puis utilisateur), et à défaut prend le modèle par défaut de la session Codex. Les efforts restent épinglés, medium pour les chasseurs et high pour les vérificateurs, et jamais hérités.

§03

Ce que fait le rail aujourd'hui

Capture (hook après gh pr create) → export de nuit → juge local à 5 h → branche improve/<skill>-<date> poussée dans claude-skills → proposition avec porte d'approbation dans le hub. L'application n'est lancée que par bun run evals apply <id>.

applyApproved greffe le dossier du skill sur main dans le clone d'intégration (~/Desktop/my-projets/.ws-integration/claude-skills), pousse, puis installSkillFromIntegrationClone (apply.ts:1269-1379) :

  • refuse si le dossier installé est un lien symbolique ;
  • refuse si le marqueur .ws-install-sha.json ne vaut pas le beforeSha de la proposition (installation divergente, ouvre un chip de rebase) ;
  • sinon supprime le dossier, recopie tout le dossier source, écrit le marqueur.

La seule racine d'installation est WORKSTATION_SKILLS_INSTALL_ROOT=~/.claude/skills (docs/evals/rail-application.md:54). Les tests passent cette racine en paramètre sous un dossier temporaire (apply.test.ts), ce qui rend l'ajout d'une seconde racine facile à tester.

Il existe déjà un rédacteur Codex, server/services/migration/codexWriter.ts, mais il sert au moteur de migration sur des fixtures et le rail ne l'utilise pas.

Conséquence : le cache ne peut pas fournir les noms de modèles, puisque les modèles réellement utilisés n'y figurent pas. Il sert seulement à vérifier qu'un effort est supporté quand le modèle y figure.

Le risque équivalent à « pas d'Opus » : l'effort par défaut est xhigh. Un sous-agent lancé sans reasoning_effort en hérite. C'est l'incident Claude du 25 août (sous-agents hérités du modèle de session, limite de 5 h atteinte) sous une autre forme.

Côté Claude, chasseurs et vérificateurs utilisent le même modèle (Sonnet) et ne diffèrent que par l'effort. Je propose le même schéma pour Codex.

Résolution proposée, au moment de l'usage

rôle review-hunter   → effort medium
rôle review-verifier → effort high

modèle, par ordre :
 1. <repo>/.codex/model-routing.json   roles["review-hunter"|"review-verifier"].model
                                      (à défaut : roles.review.model pour les deux)
 2. ~/.codex/model-routing.json        même schéma, un seul fichier à mettre à jour
                                      quand une génération de modèles change
 3. ~/.codex/config.toml               clé model (le modèle par défaut de la session)

effort : toujours celui du rôle, jamais hérité ; jamais xhigh, max ni ultra
         pour un sous-agent. Si le modèle figure dans models_cache.json et
         ne supporte pas l'effort, prendre l'effort supporté juste en dessous.
rejet du modèle au spawn : une seule nouvelle tentative avec le niveau suivant
         de la liste ; si tout échoue, ne pas passer model (défaut de session),
         en gardant reasoning_effort.

Le skill contient la procédure de lecture, jamais un nom de modèle. Seuls les fichiers de routage, que tu tiens, contiennent des noms. L'orchestrateur écrit dans sa trace le modèle et l'effort retenus par rôle, pour que le juge de nuit puisse les contrôler.

§05

La variante Codex du skill

Tout ce qui fait la valeur du skill reste mot pour mot : les deux modes, le verdict à deux portes, le balayage par classe avec sa table, la couverture 1:1 du mandat, la provenance des preuves, les champs findings, sweeps, residualRisk et checksPerformed, le second tour sur le diff du correctif. Seules changent les sections qui nomment des outils propres à Claude Code.

Claude Code (inchangé)

  • Workflow tool si disponible, sinon Agent en parallèle
  • model:'sonnet', effort medium / high
  • Agent mort : resumeFromRunId ou SendMessage
  • Correcteurs isolés : isolation:'worktree'
  • Sentinelle exigée par le hook global

Codex (variante générée)

  • Toujours le repli sans Workflow : spawn_agent avec agent_type:"default" et fork_turns:"none", puis wait_agent ; le prompt de chaque agent exige les mêmes champs de restitution
  • Modèle et effort par la résolution du §04
  • Agent mort : relancer le même message (pas de cache de run) ; send_message apparaît dans les sessions, à confirmer avant de l'écrire dans le skill
  • Correcteurs isolés : git worktree add explicite par correcteur, ou la clause d'arbre partagé
  • Sentinelle : même commande ; tant qu'aucun hook Codex n'existe, le skill dit qu'elle est déclarative

Le gabarit JavaScript du Workflow (environ 120 lignes) est remplacé par un gabarit de prompts : le même CONTEXT, la même liste de dimensions, et le format de réponse écrit en clair dans le message. Le repli exige déjà ces champs ; la variante Codex en fait le chemin unique.

§06

Garder la parité ensuite : deux options

écartée A · Appliquer la proposition aux deux installations

Simple, mais copie verbatim un texte écrit pour Claude Code. C'est l'état actuel en mieux daté, avec les mêmes consignes inapplicables. Et si quelqu'un adapte la copie Codex à la main, le marqueur la déclare divergente à chaque application.

recommandée B · Générer la variante Codex depuis la source

La source garde un seul SKILL.md. Les passages propres à un runtime sont entourés de <!-- runtime:claude --> ou <!-- runtime:codex -->. Un générateur produit chaque variante ; les propositions de nuit continuent de modifier la source seule.

Ce que B demande concrètement

  • claude-skills : scripts/build-runtime-variant.mjs <skill> --runtime codex|claude. Sans marqueur, la sortie est la source telle quelle, sans aucun remplacement textuel (c'est ce qui évite une nouvelle vague de .Codex/).
  • Test du générateur, lancé par la porte qualité de claude-skills. Il vérifie que la variante Codex :
    • ne contient ni Workflow tool, ni model:'sonnet', ni opus, ni SendMessage, ni resumeFromRunId ;
    • ne contient aucun nom de modèle daté (motif gpt-\d) ;
    • ne contient aucun chemin .Codex/ ;
    • garde les mêmes titres de section et les mêmes noms de champs de restitution que la variante Claude ;
    • a des marqueurs bien appariés.
    La variante Claude doit en plus être identique octet pour octet au SKILL.md actuel, une fois les marqueurs retirés.
  • workstation, rail :
    • une seconde racine WORKSTATION_CODEX_SKILLS_INSTALL_ROOT=~/.agents/skills ;
    • installSkillFromIntegrationClone installe la variante générée dans cette racine, avec son propre .ws-install-sha.json, la même garde de divergence et le même refus des liens symboliques ;
    • un échec côté Codex n'annule pas l'installation Claude, mais il ouvre un chip ;
    • rail-doctor signale toute copie Codex dont le marqueur est en retard ;
    • tests dans apply.test.ts avec deux racines temporaires ;
    • mise à jour de docs/evals/rail-application.md.
