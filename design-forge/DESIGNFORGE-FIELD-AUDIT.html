01 — Executive summary

Strong on what it can measure. Blind to what it must look at.

DesignForge is genuinely good at the computable half of UI quality — contrast ratios, horizontal overflow, tap-target sizes, ARIA wiring, dead code, console errors. In every run it produced at least one real, evidence-backed win. But across all three genuine runs it was consistently blind to the compositional half — the half a human designer judges by looking at a rendered page: whether the hero fills the screen, whether the header is overloaded, whether buttons sit consistently, whether the page has any visual life. Worse, it repeatedly issued premium "ship it" verdicts on dimensions it never actually tested, and its viewport coverage was inconsistent and desktop-skewed every single time.

What it does well
  • Measured contrast failures with real DOM values (automintech: 27 failing pairs root-caused to 3 tokens → correctly not shippable).
  • Found genuine engineering defects — a particles event-listener leak, a false "success" on a dead mailto form.
  • Tap-target / focus-ring / overflow gates are precise and quantitative.
  • Calibrated "is this AI slop" judgement — its not-slop calls were defensible.
Where it is blind
  • The entire first-viewport / layout-structure checklist is absent from the knowledge base — 0 of 26 reference files mention 100vh, scroll-down cues, or scroll-to-top.
  • Viewport coverage never reached the full matrix — tablet and small-mobile were skipped in 3/3 runs.
  • It rubber-stamps "responsive / footer / motion pass" on screens it never resized, scrolled, or rendered.
  • Falls back to numeric getComputedStyle checks instead of judging the rendered image.
3 / 3 genuine runs skipped tablet and small-mobile viewports — yet each still reported a responsive verdict. The user had to catch the hero, header, button and imagery defects by hand, in the next session, every time.

02 — Scope & method

What was examined

04 — Root-cause findings

Five mechanisms behind the misses

FINDING 1 · the "I'm not sure why it skips viewports" question, answered

Nothing forces the viewport sweep, and three escape hatches invite skipping it

The protocol lists nine widths (375→1920), but it is advisory. There is no binary gate that fails a run for incomplete viewport coverage, so the agent skips freely whenever it's expensive or awkward, and four distinct forces push it to:

  • Passive AUDIT is blind by construction. It can only see the screenshots handed to it. In eosa those were desktop + one generic "mobile" preset, so tablet and small-mobile literally weren't in the evidence — and instead of requesting them (as the protocol says to), it passed "responsive."
  • The preview environment can't always resize or scroll. eosa's preview was a no-op on scrollTo; home-spectors fell back to computed styles; automintech only ever used two presets. The capability the sweep depends on simply wasn't there, and the run didn't downgrade its verdict to match.
  • Time-boxing has an explicit skip. The 30-minute quick audit is defined as "375/768/1440 only" — by design it drops tablet variants and all small-mobile, with nothing flagging the omission in the report.
  • A reasoning loophole. "clamp() makes full-range pass very likely" lets the model reason its way out of testing.

And the matrix itself stops at 375px. "Smaller mobile" — 320/360, iPhone SE 1st-gen, small Android, folded devices — is not a defined checkpoint anywhere, so it can never be tested, exactly as the user observed.

FINDING 2 · false confidence

It scores categories it never observed as "pass"

The scoring model passes any category that produced no findings. But "no findings" conflates looked and found nothing with never looked. So an unscrollable preview yields "footer passes," a two-viewport run yields "responsive passes," and a 9/10 lands on a screen whose bottom half was never on screen. The honesty rules in the AUDIT protocol ("do not claim a state is missing — claim it is not evidenced") exist for findings, but there is no matching rule forbidding a pass on an unobserved dimension.

FINDING 3 · numbers over rendering

When looking gets hard, it reads computed styles instead

This is why the tool is excellent at contrast, overflow and tap-targets (all readable from the DOM) and weak at hero fill, density, proportion, button placement and visual richness (all only judgeable from the rendered image). The fallback is reasonable as a tactic, but it silently narrows the audit to the measurable subset without saying so.

FINDING 4 · animation timing

Screenshots fire mid-animation, so motion is never cleanly seen

Scroll-reveal and entrance animations were caught half-played in automintech three times. The protocol never tells the agent to settle animations (scroll to rest, wait for transitions to complete) before capturing — so motion review is unreliable and blank/odd frames risk false findings.

FINDING 5 · the checklist gap

The structural checklist the user wants simply isn't in the knowledge base

A grep across all 26 reference files confirms the absence at the source, not just in execution:

05 — Requested checks

The eleven checks to add — each grounded in the evidence

These were called out directly. For each: its current status in DesignForge, what the field evidence shows, and the concrete change to make — naming the plugin file it belongs in.

A. The hero must include a scroll-down buttonAbsent

Never checked in any run. eosa's Boutique hero shipped without the cue even though the main site already had a .hero-cue element — a parity miss the user had to dictate by hand (b68cf1e6 · L310).

RecommendationAdd a "first-viewport" detection rule to defect-taxonomy.md (new group V0 — Hero & first viewport): flag Major when a long-scroll landing hero has no visible scroll-affordance. Add the same as a required line in the BRIEF design-intent template so new builds specify it.
B. The site must include a scroll-to-top buttonAbsent

Never checked. Requested by the user in the same breath as the scroll-down cue. The unscrollable previews mean the tool never even reached the bottom of a page to notice its absence.

RecommendationAdd to defect-taxonomy.md § U1 Navigation: on any page taller than ~2 viewports, a missing back-to-top affordance is a Major finding. Pair with Finding 1's fix so the agent actually scrolls to the foot of the page.
C. The footer must be well-organised and structuredPartial

Footers appear only as a cross-page consistency check ("same height/margins on every page") and as a tap-target. There is no standalone evaluation of footer composition. In two runs the footer was never on screen at all.

RecommendationAdd a footer-structure rubric to defect-taxonomy.md: column grouping & logical sections (nav / legal / social / contact), heading hierarchy, no link dumping-ground, balanced density. Require the agent to scroll to and screenshot the footer before scoring it.
D. Analyse the header across desktop / tablet / mobile for overload & hierarchyPartial

Only one header rule exists — mobile tab-bar ">5 tabs." Desktop/tablet information-density is uncovered. home-spectors scored Layout 92 and was then told the header was "trop touffu" (too cluttered); eosa's mobile wordmark wrap was caught by a different skill, not DesignForge.

RecommendationAdd a header-density check to defect-taxonomy.md § V7 evaluated per breakpoint: count primary nav items, flag competing emphasis, assess whether secondary actions should collapse into a menu on tablet. Wire it into the Phase 2 viewport sweep so it's judged at each width, not once.
E. Information density — alignment, margins, spacingPartial

Spacing/density is well covered (§ V2). Text alignment — centered-vs-left as a deliberate choice — exists only as a single fix-line ("do not center long body paragraphs"). It is not a systematic pass, and the computed-style fallback can't judge it.

RecommendationPromote text-alignment to a first-class check in analysis-protocol.md (Pass 3): flag centered multi-line body copy, centered long-form blocks, and mismatched alignment between adjacent sections; confirm margins/measure against the existing 45–75ch rule.
F. Buttons must be well-placed and consistent throughoutPartial

Button states and competing CTAs are covered; button placement and positional consistency are not. eosa's user insisted the scroll-up and WhatsApp buttons be "la même taille… bien positionnés… en desktop et sur mobile. C'est très important." home-spectors had a wrapping label with a tiny disconnected arrow — neither was flagged.

RecommendationExtend defect-taxonomy.md § V6 / § V7: verify floating-action and repeated buttons share size, corner, icon treatment, and screen position across pages and breakpoints. Add to the cross-region comparison in analysis-protocol.md.
G. The hero must fill the full viewport (100vh) on every device — detect when it doesn'tAbsent

The headline gap. 100vh / full-viewport appears in zero reference files and was measured in zero runs. This is precisely measurable from the DOM (hero block height vs innerHeight), so it plays to the tool's strength — it just isn't asked for.

RecommendationAdd a quantitative rule to the new V0 — Hero group: at each device width, measure the hero section's rendered height against viewport height; flag Major when a landing hero falls short of (or overflows) the full viewport. Make it part of the Phase 2 per-breakpoint checklist so it runs on desktop, tablet, mobile and small-mobile.
H. The hero must be visually engaging (animation, background imagery, depth)Negative-only

"Hero" appears only as a slop warning (oversized italic-serif hero, gradient hero). There is no positive check for engagement. eosa's user drove an entire image program afterwards and flagged that the hero card covered people's faces and that Contact/Partner pages had no imagery at all.

RecommendationAdd a hero-engagement rubric (balancing the existing anti-slop rules): is there a background image / motion / depth treatment, is the focal subject unobstructed, is the imagery present and on-brand. Sits in defect-taxonomy.md § V0, cross-referenced from anti-slop-rules.md so "engaging" never means "slop."
I. The site should use appropriate animation, background imagery & visual richnessPartial

Motion quality when present is well handled (easing, fps, reduced-motion). But the absence of motion/imagery is never flagged — a flat, static, image-less page passes the taxonomy clean. Every richness upgrade across the runs was user-initiated.

RecommendationAdd a "visual richness / motion presence" enhancement check: flag pages with no entrance/scroll motion, no background imagery, and no depth as an Enhancement-to-Major opportunity. Belongs in defect-taxonomy.md § U6 / a new "richness" note, and in the BRIEF spec language.
J. It must always test every viewport, including smaller mobileInconsistent

The protocol describes the sweep well, but nothing enforces it and three forces undercut it (Finding 1). Result: tablet skipped in 3/3 runs, small-mobile in 3/3, with a responsive verdict issued anyway. The matrix also has no checkpoint below 375px.

RecommendationThree changes: (1) add 320/360 small-mobile to the matrix in design-system-reference.md; (2) add a binary gate "viewport coverage" to scoring-and-report.md — a responsive verdict is invalid unless mobile, small-mobile, tablet and desktop were each actually rendered; (3) forbid gates from reporting widths that were never set, and require the report to list which viewports were and weren't covered.

06 — Field follow-up

Two more misses — now confirmed in the code

After the first pass, two further defects surfaced on the automintech site that DesignForge had audited and passed. I confirmed both directly in the source (read-only). They generalise into the new checks below.

CONFIRMED DEFECT 1 · CRITICAL · WCAG 1.4.3

The translucent sticky header lets content bleed through and breaks nav legibility

The header has no opaque background of its own. Once scrolled it takes the shared .glass-panel utility — rgba(251,250,247,0.72) light, rgba(16,21,29,0.66) dark, plus a 20px blur — with no opaque fallback and no scrim. So ~28–34% of whatever scrolls behind it composites through. The worst offender is the large Fraunces serif <h2> (e.g. "Un parcours de livraison clair"): its near-black / near-white strokes survive the blur and ghost over the nav. Inactive nav text collapses from a passing ~5:1 to 2.91:1 (light) / 2.69:1 (dark) against the bleed-through — below the 4.5:1 AA floor, on the site's most-used control.

.glass-panel{ background: rgba(251,250,247,0.72); backdrop-filter: blur(20px) saturate(1.4);} .dark .glass-panel{ background: rgba(16,21,29,0.66);}

automintech · src/styles/globals.css:222–238 · Header.tsx:86–91 — the only filled-header style; no opaque fallback, no scrim

Why DesignForge missed it: it evaluated the header against its design-token surface colour and never scrolled high-contrast content underneath it. Paste-ready fix: give the scrolled header a dedicated header-solid variant at ~0.94/0.92 alpha with an @supports not (backdrop-filter) opaque fallback — and keep .glass-panel for the drawer/overlays.

CONFIRMED DEFECT 2 · MAJOR · mobile only

On mobile, multi-column sections collapse into a disorganised stack

Three sections in components/views/Home.tsx — the stats cards, the "parcours" method steps, and the "Comment nous collaborons" steps — are desktop grids (md:grid-cols-3, lg:grid-cols-4, lg:grid-cols-[5rem_1.1fr_1.3fr]) that collapse to a single column purely by DOM source order — there is not one order-* utility in the file. The result: the icon and the tiny index number each become their own full-width row floating above the heading they label, and desktop-only spacing (mt-5, gap-6) with no lg: override becomes oversized vertical voids. Icon / number / text read as three disconnected fragments — exactly what you described.

Why DesignForge missed it: it only looked at desktop / static screenshots and never resized to ~390px to read the post-collapse vertical order. Paste-ready fix: regroup each unit so the icon + index number share a row with (or bracket) their heading — via a flex wrapper or a lg:hidden inline number — and move the large gaps behind the lg: prefix.

The cure is the same discipline the viewport-coverage gate enforces: look at the state where the bug actually appears.

07 — The orchestrated-audit idea

Dynamic workflows: a good scale tool, not the root-cause fix

The proposal — capture every viewport to a temp folder, fan out parallel agents to scrutinise the screenshots while a live agent scrolls in parallel, then clean up — is a sound instinct. But pressure-tested against what actually broke in the field, it is a scale tool, not the fix, and it carries one trap.

Every field failure was a missing enforcement gate or a missing checklist entry — not a shortage of parallelism. eosa passed "responsive/footer/motion" in a preview that couldn't scroll; home-spectors reasoned "clamp() makes full-range pass very likely"; automintech reported a clean 1920px pass on a width it never rendered. Fanning out screenshot-lenses over the same evidence reaches the same verdict — in parallel, at several times the cost:

"A parallel set of agents over the same evidence still passes unobserved categories… and worse, an aggregation layer can manufacture a union 'responsive: pass' that no single shard actually earned. Orchestration must be built on top of the guardrails, or it parallelizes the exact lie the audit exposed."

adversarial critique · workflow follow-up

So: guardrails first, orchestration second, and only in one safe form. If you build it, it must obey these:

  • Live-first — screenshots are evidence, never the substrate. A folder of stills can't show hover/focus, scroll-down / scroll-to-top affordances at the page foot, animation, keyboard order, or reflow at unseen widths — the whole compositional half. The fan-out must drive a live app; captures are only what it records.
  • Stamp every capture with provenance — {route, viewport, scrollY, animations_settled, time} — and forbid any finding or pass that references a state not in the manifest. This kills phantom-viewport passes and mid-animation false frames.
  • Never delete evidence on success. The "ship it" verdict is exactly the one a user needs to dispute; write to a run-scoped, .gitignored folder, keep it, make cleanup opt-in. (This whole report was only possible because past evidence survived.)
  • Dedupe before aggregating, bound the cost, fail closed. Collapse one defect seen at nine widths into a single finding with a viewport list; a crashed lens marks its dimension not-evidenced, never a silent pass.
  • Opt-in, for large apps only. Inline stays the default (and is required for pasted screenshots). Orchestration earns its keep on genuinely large live jobs (≈15+ routes × 4 device classes), route-sharded so each agent keeps a clean context — a real win in capacity and wall-clock, not in "seeing better."

A fitting footnote: while running this very analysis, one of the parallel workflow agents silently returned a placeholder instead of its result — the run didn't notice until a second agent flagged it. That is the orchestration trap in miniature, and the reason "a failed lens must mark its dimension not-evidenced, never pass" is a hard requirement, not a nicety.

08 — What to change first

A prioritised fix order

The original eleven checks plus the two field-confirmed defects cluster into a handful of edits. In leverage order:

Add a binary "viewport coverage" gate · highest leverage

One rule in scoring-and-report.md fixes the single most consistent failure: no responsive verdict unless small-mobile, mobile, tablet and desktop were each rendered. This alone would have blocked all three premium verdicts.

Add the V0 — Hero & first-viewport group · covers A, G, H

Full-viewport (100vh) measurement, scroll-down cue presence, hero engagement. All three are the user's top pain and two are precisely measurable — they play to the tool's existing strengths.

Forbid "pass" on unobserved dimensions · trust fix

Extend the honesty rule so a category that was never rendered/scrolled is reported as not evidenced, never as a pass. Detect no-scroll/no-resize environments and downgrade the verdict instead of inflating it.

Add the page-structure & field-confirmed checks · covers B, C, D, F + §06

Scroll-to-top, footer organisation, per-breakpoint header density, button placement consistency — plus the two confirmed misses: sticky-header bleed-through (V3-09 + the scroll-composite sweep) and mobile reflow ordering/grouping (V5-06, V2-07). A coherent batch for defect-taxonomy.md, testing-protocol.md and the cross-region comparison.

Add density/alignment & richness passes · covers E, I

Promote text-alignment to a first-class pass and add a motion/imagery-presence check, so flat and mis-aligned pages stop scoring clean.

Settle animations before capture & extend the matrix · covers J, Finding 4

Add a "scroll to rest, wait for transitions" step before screenshots, and add 320/360 to the viewport matrix.

Only then, the orchestrated mode · optional · large apps

Build the dynamic-workflow fan-out last, route-sharded over the live app, with provenance-stamped captures, no cleanup-on-success, and the §07 guardrails inherited. Never as a substitute for the gate.

One structural note. Several of these — full-viewport, footer, scroll-to-top, richness — require seeing the whole rendered page at each width. DesignForge's recurring habit of falling back to getComputedStyle defeats them. The fixes above only land if the run is required to actually render and scroll each viewport; otherwise the new checks will be skipped the same way the old ones were.
