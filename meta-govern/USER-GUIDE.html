meta-govern — Quick Start for the User

User-facing guide. Not loaded by Claude. Read this whenever you need a refresher on what meta-govern does and how to invoke it.

# TL;DR

meta-govern is your global Claude Code governor. One skill. Lives at ~/.claude/skills/meta-govern/. Works in any project on your machine. Replaces the manual "remember to set up CLAUDE.md, hooks, skills, agents, source of truth, govern-claude" ritual you do every time you start a new project.

It does NOT replace skill-creator, create-subagent, session-review, domain-driven-design, or your project-level govern-claude. It orchestrates them.

# How to invoke

Just describe what you need. Claude will trigger meta-govern via its description matching:

You say meta-govern does
"Set up Claude for this project" BOOTSTRAP — full workflow install
"Audit my Claude setup" / "drift check" / "what's missing" AUDIT — read-only inventory + findings
"Upgrade my workflow to v2" / "migrate to new palier" MIGRATE — incremental update
"Update meta-govern with this new research doc" EVOLVE — meta-govern self-update
"What palier am I at" / "should I add X" ADVISE — read-only recommendation

You can also explicitly say /meta-govern or "use meta-govern".

# What gets installed in BOOTSTRAP

After you approve the scaffold plan, meta-govern installs into your project:

# Sources of truth (you fill in content via interview)

  • docs/<project>-spec.md — FUNC-XX, RA-XX, VAL-XX
  • docs/data-model.md — schema, contracts
  • docs/composants/catalogue-composants.md — C-XX UI catalog

# .claude/ skeleton

  • CLAUDE.md (≤120 lines) — router, source-of-truth pointers, model+effort defaults
  • .claude/settings.json — hooks declarations (PostToolUse, Stop, PreCompact)
  • .claude/rules/*.md — 8 path-scoped rules (clean-code, file-size-budget, ui-components, data-layer, testing, spec-protocol, parallel-dispatch, claude-config-style)
  • .claude/skills/ — 5 core skills (brainstorm, write-plan, execute-plan, quality-gate, govern-claude)
  • .claude/agents/ — 6 core agents (implementer, ui-implementer, spec-reviewer, code-quality-reviewer, persona-simulator, codebase-reality-check)
  • .claude/hooks/ — 5 hooks (track-workflow, enforce-workflow, precompact-handoff, postcompact-reinject, session-start-env-check) + lib/hook-utils.mjs
  • .claude/scripts/ — file-size-growth-guard.mjs + quality-checks/ suite

# Other

  • package.json scripts: validate, validate:fast, quality:check, quality:check:staged, quality:check:critical, size-guard
  • .husky/pre-commit — lint-staged + size-guard + quality-check (staged scope)
  • .gitignore additions: .claude/settings.local.json, .claude/tmp/, HANDOFF.md (optional)
  • HANDOFF.md — auto-generated by PreCompact hook
  • docs/backlog-deferred.md — deferred-issue ledger
  • docs/architecture/ddd-decision.md — DDD scorecard outcome

# What does NOT happen automatically

  • No git commits. You commit.
  • No ~/.claude/settings.json modifications. Global config is yours.
  • No deletions. meta-govern only adds. Ever.
  • No silent overwrites. Every change is previewed.

# Evolution paliers (0-6)

Per references/evolution-roadmap.html. Your project starts at Palier 0 (greenfield) and earns its way up:

  • Palier 0: Brand new project (no .claude/ yet)
  • Palier 1: Initial bootstrap (5 skills, 4 agents, 3 hooks, 8 rules)
  • Palier 2: Spec maturity (≥30 FUNC IDs → adds spec-tracer, qa-plan)
  • Palier 3: Multi-dev (worktree workflow, spec-reviewer split, subagent-plan-edit-guard hook)
  • Palier 4: CI ready (GitHub Actions, release-notes skill)
  • Palier 5: Dual-runtime (.codex/ adapter, AGENTS.md mirror)
  • Palier 6: 30+ DEFERRED entries (backlog automation, next-deferred-id.mjs)

meta-govern detects your palier and proposes promotion when triggers met.

# Self-evolution

When new Claude Code features ship or new research docs land:

  1. You drop the doc in ~/.claude/skills/meta-govern/references/inbox/
  2. Run "evolve meta-govern with this new doc"
  3. meta-govern proposes reference + template updates
  4. You review + accept
  5. version.json bumps
  6. Existing projects become MIGRATE candidates

# Troubleshooting

Symptom Likely cause Fix
Skill doesn't trigger when I ask Description not matching Be more explicit: "use meta-govern" or "/meta-govern"
BOOTSTRAP overwrote a file I had Should NEVER happen — file diffs are previewed File a lesson in lessons-log.html, fix the validator
AUDIT reports defensive scaffolding I want to keep Add file path to .meta-govern-ignore Document why in the file's frontmatter meta-govern-ignore-reason:
MIGRATE breaks my hooks New hook lib is incompatible Roll back via git, run AUDIT to identify the diff, manually adapt

└── agents/               # 9 sub-agents the skill orchestrates

# Maintenance cadence (you run these)

  • Every 2-4 weeks: AUDIT each active project. Apply proposed diffs.
  • After every session-review: Append lessons to references/lessons-log.html.
  • When new Claude model ships: EVOLVE mode + MIGRATE all projects.
  • When you change stacks (e.g., Convex → Supabase): Add a stack convention pack references/stack-<name>.md.

# Philosophy

"Inventories rot, grep stays fresh." Every time you would catch yourself building the same skill, agent, hook, or rule for the third project in a row, that's the signal to extract it into meta-govern's templates instead.

Built from the synthesis of:

  • Groupe Gilbert "Temps Chantier" (production, 15 skills, 4 agents, 11 hooks, 8 rules, dual-runtime architecture)
  • Brillance Décor Inc. (mid-build, 18 skills, 5 agents, 3 hooks, 8 rules, palier roadmap)
  • 5 research documents on Claude Code architecture, DDD, effort levels, progressive disclosure, skill design.

The user's full institutional memory, encoded once, applied everywhere.
