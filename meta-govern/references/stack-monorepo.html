Stack Pack — Monorepo (pnpm + Turborepo or Nx)

When meta-govern detects: pnpm-workspace.yaml exists at root AND (apps/ exists with ≥1 child OR packages/ exists with ≥1 child) AND (turbo.json OR nx.json).

# When monorepo wins

A monorepo earns its keep when at least one of these is true:

  • 2+ deployables (e.g., apps/web + apps/api + apps/admin).
  • Genuine shared packages (UI lib, schemas, domain) reused by 2+ apps.
  • Graph-aware CI matters (affected checks, distributed cache).
  • A team boundary aligns with a package boundary.

If none of those are true, stay single-app. A monorepo with one apps/web/ and an empty packages/ is overhead with no payoff.

This is archetype D in project-archetypes.html.

# Turborepo vs Nx

Need Choose
Thin orchestration, low ceremony, focus on package + task graph Turborepo
Graph-aware AI workflows (configure-ai-agents, MCP server, generators) Nx
Affected checks + distributed cache + multi-language (Python/Go/JS) Nx
Just need parallel builds and remote cache for JS/TS Turborepo

Default: Turborepo unless the user explicitly wants Nx's AI/affected affordances or runs CI at a scale where graph distribution matters.

# Layout

workspace/
├─ apps/
│  ├─ web/                # palier-1 scaffolded per stack-react-vite or stack-nextjs
│  ├─ admin/              # optional second frontend
│  ├─ api/                # optional separate API
│  └─ docs/               # optional docs site
├─ packages/
│  ├─ ui/                 # shared component library
│  ├─ schemas/            # shared Zod schemas (boundary contracts)
│  ├─ domain/             # shared domain types / pure logic (when DDD applies)
│  ├─ api-client/         # generated typed client (when api is in-tree)
│  ├─ config-eslint/      # shared eslint config
│  ├─ config-typescript/  # shared tsconfig base
│  └─ utils/              # genuinely shared helpers (small)
├─ docs/
│  ├─ architecture.md     # repo-wide architecture
│  ├─ agent-playbook.md   # how to add a feature, endpoint, package
│  ├─ decisions/          # ADRs
│  ├─ testing.md
│  └─ security.md
├─ .claude/               # one root .claude — palette shared across apps
├─ .husky/
├─ CLAUDE.md              # one root CLAUDE.md; per-app deltas via .claude/rules paths
├─ pnpm-workspace.yaml
├─ turbo.json | nx.json
├─ package.json
└─ README.md

# CLAUDE.md strategy

One root CLAUDE.md. Per-app deltas live in .claude/rules/<app>-*.md with paths: apps/<app>/** — not in nested apps/<app>/CLAUDE.md files. Reasons:

  • Multiple CLAUDE.md files compound standing-context cost.
  • The four-tier architecture's path-scoped rules already handle locality.
  • Compaction recovery is one file, not N files.

Exception: if an app has materially different commands (e.g., apps/api uses Bun + drizzle while apps/web uses Node + Next), accept a thin app-level CLAUDE.md that pointer-references the root.

# Skills to install (BOOTSTRAP)

In addition to the 5 core skills:

  • frontend-design, ship-polished-ui, seo-visibility — when any frontend app exists
  • simplify (palier 2+) — pruning shared packages

# Agents to install

In addition to the 6 core agents:

  • package-cohesion-reviewer (palier 3+, project-level) — checks that a new shared package has 2+ real consumers before approval

# Hooks to install

In addition to the 5 core hooks:

  • (Optional, palier 3+) package-import-guard.mjs — block PRs that add a new packages/<x> without ≥2 consumers

# Path-scoped rules to install

In addition to the 8 core rules:

  • package-discipline.md (paths: packages/**):
    • One package = one cohesive concern
    • No app-specific code in packages
    • Public API exposed via index.ts; no deep imports from consumers
    • Each package has its own tests
  • feature-organization.md (paths: apps/**/src/features/**, apps/**/src/routes/**) — see template
  • App-specific path rules per stack pack (Next, Vite)

# Tooling stack

  • pnpm 9+ workspace + catalogs (centralized version management)
  • TypeScript strict mode with shared packages/config-typescript
  • Turborepo OR Nx (chosen per matrix above)
  • Knip + dependency-cruiser + eslint-plugin-boundaries — palier 1 for archetype D (see tooling-architecture-checks.html)
  • Changesets for versioning (when packages are published)

# Validate command

# Turborepo

{
  "scripts": {
    "dev": "turbo run dev",
    "build": "turbo run build",
    "typecheck": "turbo run typecheck",
    "lint": "turbo run lint",
    "test": "turbo run test",
    "validate": "turbo run typecheck lint test build && bun run lint:dead && bun run lint:deps && bun run quality:check",
    "lint:dead": "knip",
    "lint:deps": "depcruise --config .dependency-cruiser.cjs apps packages",
    "quality:check": "node .claude/scripts/quality-checks/index.mjs"
  }
}

turbo.json defines task dependencies (dependsOn: ["^build"]) so the graph is respected.

# Nx

{
  "scripts": {
    "validate": "nx affected -t typecheck lint test build && bun run quality:check",
    "validate:full": "nx run-many -t typecheck lint test build",
    "graph": "nx graph"
  }
}

Nx's affected is the killer feature: only validates packages whose graph is touched by the diff.

# Common gotchas

  • Empty packages/ with one config package — collapse back to single-app until reuse is real.
  • packages/utils becoming a dump — split by concern (packages/dates, packages/strings) or push into the consuming app.
  • App importing from another app (apps/web imports from apps/admin) — forbidden; promote the shared code to a package.
  • Circular deps between packages — caught by dependency-cruiser; usually means a package needs splitting or merging.
  • pnpm install slow — enable pnpm catalogs to deduplicate version drift.
  • Per-app node_modules — fine in pnpm (symlinked); don't try to flatten.

# Source-of-truth doc structure

Two layers:

  1. Repo-wide: docs/architecture.md, docs/agent-playbook.md, docs/decisions/
  2. Per-app: apps/<app>/docs/<app>-spec.md, apps/<app>/docs/data-model.md, apps/<app>/docs/composants/catalogue-composants.md

The root CLAUDE.md Source de vérité block points at the repo-wide docs and lists per-app docs.

# Promotion signals

  • Adding a new apps/<x>/ → run BOOTSTRAP scoped to that app, reuse the root .claude/.
  • Adding a new packages/<x>/ → require ≥2 consumers (or document why); add package-cohesion-reviewer review step.
  • Going from 2 apps to 5+ apps → promote to palier 4 (CI graph-aware) and lock in Nx if not already.
