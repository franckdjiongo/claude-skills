Governance Cadence — Audit Rhythm & Self-Healing

Source: synthesis of Claude Code Architecture Research.md, observation of Temps Chantier's governance-matrix.md (60+ lessons) and Brillance Décor's evolution-roadmap.html + session-lessons.md.

# The cadence (what to audit when)

Trigger What to do
Every 2-4 weeks during active dev Run AUDIT mode on each active project
After major refactor (≥10 files) Run AUDIT
After adding any skill / agent / hook / rule Run AUDIT (specifically check wiring)
Before a milestone (feature ship, backend launch, multi-runtime) Run AUDIT
When Claude Code version bumps with new feature Run EVOLVE on meta-govern; consider MIGRATE per project
When Claude model ships (Opus 4.8, etc.) Run EVOLVE; rewrite model-specific defaults (model-effort-defaults.html); MIGRATE projects
When session-review surfaces a recurring pattern Append to lessons-log.html; consider EVOLVE
When the user says "drift" / "audit" / "what's missing" Run AUDIT
When a guard suite grows large (>~1000 cases, so a spot read no longer proves coverage) Run a mutation-testing ritual: in a throwaway branch, flip each guard's decision condition (deny↔allow, invert the target regex) and confirm a test turns red; a surviving mutant marks a vacuous assertion — the suite runs but does not catch. Fix the test, discard the branch
On each autonomous (headless) run wakeup (MG_HEADLESS_RUN=1) Do not sweep every project each night. Weighted-sample the active projects — weight up recent-drift and higher-palier ones — and AUDIT that subset within the run's SLA (a fixed wall-clock budget), so each project is reached on a predictable cadence without blowing the window

# Self-healing: the lesson lifecycle

The user's institutional memory grows by accumulating lessons. The lifecycle is precise:

1. Observed (during work or session-review)
   ↓
2. Recorded as TEXTUAL RULE
   - In CLAUDE.md if always-on
   - In a path-scoped rule if file-type-specific
   - In a skill body if multi-step workflow
   - In an agent system prompt if role-specific
   ↓
3. Recurs despite the textual rule
   ↓
4. Promoted to PATH-SCOPED RULE (if not already)
   - Add `paths:` frontmatter
   - Loaded only when relevant
   ↓
5. Still violated under load
   ↓
6. SHADOW MODE — a deterministic hook that observes, does not deny
   - Logs every hit as JSONL (`{ ts, command, target, vector, mode:'shadow' }`)
   - Measures the true hit rate and any false positives on real sessions
   - Promotes to enforce via `<GUARD>_ENFORCE=1` once the log reads clean
     (e.g. `BASH_WRITE_GUARD_ENFORCE=1` turns src/** writes from log to deny)
   ↓
7. DETERMINISTIC HOOK (enforce)
   - 100% enforcement at the cost of zero context
   ↓
8. TEST THE HOOK
   - A hook that throws exits 0 and blocks nothing — the guard silently
     does not exist. Ship its test alongside it, exercising the BLOCK path
     AND the ALLOW path
   - The loop closes: incident → lesson → rule → shadow → hook → TEST of the hook

This is the "rule emerges from violation" cycle observed in Temps Chantier:

  • state-context-leak.md (rule) → emerged after BUG-03, BUG-06, BUG-04, #5a, #5b, #8 all reproduced the same class
  • subagent-plan-edit-guard.mjs (hook) → emerged after textual rule violations under load
  • agent-dispatch-preflight.mjs (hook) → emerged after manual rituals were skipped
  • bash-write-guard.mjs (shadow → enforce) → the Edit-scoped docs guard had a Bash blind spot; a companion hook first shadow-logged src/** writes, then flipped to deny under BASH_WRITE_GUARD_ENFORCE=1, each vector covered by a block/allow test

meta-govern's job is to detect when a lesson recurs (via the lessons-log.html append-only journal) and propose the promotion to a higher tier.

# Periodic re-evaluation

Every 6 months OR when the user runs EVOLVE mode:

  1. Read all lessons since last re-eval
  2. Classify by Recurrence
  3. For Recurrence ≥ 3 → check whether the lesson has been promoted (rule → hook)
  4. For Type=ARCHITECTURE → check whether a new reference is justified
  5. For Type=MODEL → check whether existing references are stale (e.g., Sonnet 4.6 → Sonnet 5, Opus 4.7 → 4.8)
  6. Bump version per semver

# Anti-fatigue principles

The user said: "à chaque nouveau projet, j'ai l'impression de toujours recommencer les mêmes choses". The cadence above prevents this:

  • Once promoted, lessons stay promoted. No "I'll do it manually this time."
  • BOOTSTRAP installs the full stack. Never partial. Reduce decisions per project.
  • EVOLVE mode handles model upgrades. The user doesn't manually rewrite prompts when Opus N+1 ships.
  • Stack convention packs (Power Platform, Convex, Vite) keep stack-specific lessons in one place.
  • Periodic AUDIT detects drift early. A 3-line drift caught in week 2 is faster to fix than a 50-line rewrite in month 3.

# Self-audit (meta-govern auditing itself)

Quarterly OR on EVOLVE invocation:

  1. Run node scripts/self-audit.mjs
  2. Check own ~/.claude/skills/meta-govern/SKILL.md against the same rules it enforces (≤5K words, valid frontmatter, no defensive scaffolding, etc.)
  3. Check templates haven't drifted (templates should be representative of what user actually uses now)
  4. Check lessons-log.html is being maintained
  5. Check version.json changelog matches actual changes since last bump
  6. Output ~/.claude/skills/meta-govern/SELF-AUDIT.md with findings

If meta-govern fails its own audit → that's a P0. Fix immediately.

# Automating the cadence (optional)

The cadence above is documented as ritual. To make it autonomous:

  • Use /schedule (built-in) to create a recurring scheduled task that runs a meta-govern AUDIT every 2-4 weeks per active project.
  • Use /loop for ad-hoc polling within a session.
  • Use CronCreate for cron-style scheduled remote agents.

Sample /schedule invocation:

/schedule "Run meta-govern AUDIT on the active project; report findings; if any CRITICAL/HIGH, summarize at top." --cron "0 9 * * 1" --branch main

(The user owns the scheduling decision. meta-govern documents the cadence; it does not auto-create scheduled tasks. Self-evolution stays under human control.)

# Final principle

"Inventories rot, grep stays fresh."

Don't pre-compute the user's project state into the skill. Discover it on every invocation. The skill's intelligence is in patterns + decision trees + scripts that observe the project, not in cached snapshots that describe it.
