Subagent — Canonical Structure

Source: Claude Code Architecture Research.md, Progressive Context Disclosure for Claude Code on Windows.md, observed patterns in user's existing agents.

# File structure

A subagent is a single .md file:

.claude/agents/<agent-name>.md      # project-level
~/.claude/agents/<agent-name>.md    # user-level

There is no folder structure. All content lives in the single file.

# Frontmatter — required

---
name: agent-name                    # kebab-case
description: |                      # describes role + when to invoke + required context
  [Role / expertise — 1 sentence].
  Use this subagent for [task type]. Required context: [list of inputs].
  Returns [output shape]. [Verdict / disposition options].
tools: Read, Grep, Glob, Bash       # tools the agent can use
---

# Frontmatter — common optional fields

Field Use when
model: opus|sonnet|haiku Pin model independent of session default
effort: low|medium|high|xhigh Always set this. Subagents do not inherit session effort.
permissionMode: plan|edit|... Constrain agent to plan-mode (read-only) or edit-mode
color: red|green|blue|purple|... Visual distinction in dispatch UI
memory: project|user|local Persistent memory file scope
isolation: worktree Run in a temporary git worktree (isolated copy of repo)
hooks: Subagent-scoped hooks (only fire when this agent is active)
mcpServers: ... List of MCP servers this agent can access
skills: skill-1, skill-2 Skills available to this agent (NOT inherited from parent)

skills: and plugin scope. A skills: value may legitimately resolve to a plugin-provided skill (e.g. ship-polished-ui, provided by the design-studio plugin), not just a user- or project-scope skill. Claude Code resolves a bare skill name via the priority cascade enterprise > personal > project > plugin, so a bare name with no matching skill under ~/.claude/skills/ or <project>/.claude/skills/ is not dangling — check the plugin scope (~/.claude/plugins/) before flagging it. Prefer the bare name over the fully-qualified plugin:skill form: bare is functional, keeps a project free to shadow the skill with its own copy, and does not hard-bind to a plugin name that may be renamed. (The one form that genuinely fails is when the providing plugin is absent entirely — neither bare nor namespaced resolves then.)

# Effort frontmatter — by role

Per model-effort-defaults.html:

Role Suggested effort
Mechanical (lint-fix, git-publisher, file-mover) low
Bulk implementer (per-task TDD-light) medium
Reviewer / researcher / auditor high
Planner / architect / migration orchestrator xhigh

# Description shape

[Role expertise — 1 sentence with strong verb].
Use this subagent when [task triggers].
Required context: [list of inputs the caller MUST provide].
Returns [structured output shape].
Verdict / disposition: [e.g., PASS|FAIL|FINDINGS|BLOCKED].
Distinct from [sibling agent] (which does X) — this agent [unique purpose].

Good description (TC reviewer):

Foreground-only code reviewer for Temps Chantier per RIGOROUS task or per group.
Required context: scope contract (diff-only / files-modified / full-audit), the
plan task being reviewed, the diff range. Returns 3 sections (Findings / Notes /
Verdict). Verdict: PASS | FINDINGS | BLOCKED. Severity-tagged findings (C/H/M/L).
Pre-existing issues go under `## Pre-existing (out of scope)` at INFO. Distinct
from spec-reviewer (which checks against spec/AC) — this agent reviews code
quality (correctness, regressions, testing, dead code, data contracts).

Bad description:

Reviews code.

# Body length

  • Recommended: ≤500 lines
  • Hard cap: ≤1000 lines (the user's project agents max around 200 lines)

# Subagent doesn't auto-inherit

Subagents do NOT inherit:

  • Skills (must list in skills: frontmatter)
  • Session effort (must set effort: frontmatter)
  • Hooks (must declare in hooks: frontmatter, scoped to this agent)
  • MCP servers (must list in mcpServers: frontmatter)
  • CLAUDE.md (separate context entirely)

The subagent starts fresh. The agent's description + body is the entire prompt.

# Subagent context isolation

Subagents have fresh context:

  • They cannot see the session that dispatched them
  • They cannot see other subagents' work
  • They cannot delegate to other subagents (1-level only)
  • They produce a single summary back to the parent

This is the isolation principle — the user gets parallel, independent specialists.

# Subagents-as-skills confusion (DON'T)

A skill teaches the current context how to do something. A subagent delegates the work to another context and gets a summary back.

If you need:

  • Skill activation from main context → skill
  • Fresh isolated specialist → subagent
  • Both → skill that explicitly dispatches a subagent (agent: frontmatter or in-body Agent call)

# Plugin subagent restrictions

If the agent ships in a plugin:

  • ❌ hooks: is silently ignored
  • ❌ mcpServers: is silently ignored
  • ❌ permissionMode: is silently ignored

Plugin agents must rely on tools + body. For full control, ship as user/project agent.

# Memory pattern

---
name: long-running-researcher
memory: project           # writes to .claude/memory/long-running-researcher/MEMORY.md
---

First 200 lines of MEMORY.md are auto-injected on each invocation. If exceeds 200 → agent is instructed to curate.

# Hooks attached to subagents

---
name: my-implementer
hooks:
  PreToolUse:
    Edit|MultiEdit:
      - command: ".claude/hooks/subagent-plan-edit-guard.mjs"
---

The hook only fires when THIS agent is the one calling Edit/MultiEdit. Used for scoped enforcement (e.g., implementers blocked from editing plan files).

# Worktree isolation

---
name: speculative-refactorer
isolation: worktree       # creates temp git worktree; agent works on isolated copy
---

If the agent makes no changes → worktree auto-cleaned. If it makes changes → worktree path + branch returned in result.

Used for: speculative refactors, risky experiments, A/B implementations.

# Authority hierarchy (in agent prompts)

For reviewers/auditors, embed:

## Authority hierarchy

When sources conflict, follow this order:
1. Task acceptance criteria
2. Plan
3. Design (spec)
4. Canonical docs (3 sources of truth)
5. CLAUDE.md
6. Common sense / engineering principles

Without this, the agent will arbitrate poorly.

# Anti-patterns recap

❌ Subagent-from-subagent dispatch (forbidden, fails) ❌ Background reviewers (0-byte output) ❌ Skills not declared in frontmatter (subagents don't auto-inherit) ❌ No effort: set (inherits session xhigh; mechanical agents waste tokens) ❌ Defensive scaffolding in agent body ("MUST always", "double-check") — Claude 4.7+/5-family anti-pattern ❌ A subagent dispatched to verify the dispatcher's own output — current models already self-verify, and the extra pass costs without adding (distinct from the reviewer loop, where the reviewer reads someone else's diff against the spec) ❌ Delegating work you could finish in a handful of tool calls, or spawning several agents where one suffices — Opus 5 delegates readily; the payoff threshold is genuinely independent, sizeable tracks (p.164, p.166) ❌ Plugin agents with hooks: / mcpServers: / permissionMode: (silently ignored) ❌ Required context not documented in description (callers dispatch without context, agent flounders)
