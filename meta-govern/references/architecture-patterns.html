Architecture Patterns — Layout & Boundary Catalog

Source: synthesis of LLM-friendly project architecture for AI coding agents in 2026.md plus existing meta-govern conventions. Cross-cuts every stack pack.

# Why this exists

Stack packs (React+Vite, Next.js, Convex, Power Platform) say which framework. DDD scorecard says whether to model the domain explicitly. Neither answers how to lay out the source tree. This catalog does.

The recommended default for 2026 agentic coding is:

Framework-native shell + feature-first vertical slices + typed contracts + modular-monolith mindset.

Five reasons agents do better with this:

  1. Routes/entrypoints stay where the framework expects them — discoverability is free.
  2. Most edits land inside one feature folder — locality of change.
  3. Shared packages exist only when reuse is real — no shared/utils/helpers dump.
  4. Boundary files are obvious — server-vs-client, route-vs-domain, app-vs-package.
  5. Validation surfaces (validate) are unambiguous and stack-agnostic.

# Pattern matrix

Score is agent-readability, not human-readability. [Synthesis from research doc.]

Pattern Score Best for Anti-signal
Framework-native + feature-first 9/10 Default for most apps (React+Vite, Next, SvelteKit, Power Apps code apps) None — start here
Vertical slice 8.5/10 CRUD-heavy apps, internal tools, BFFs Heavy cross-feature physics simulation, real-time engines
Modular monolith 8.5/10 Production SaaS / full-stack products, palier 3+ Tiny prototypes
Feature-Sliced Design (light) 8/10 Mid-size+ frontends with multiple domains Throwaway prototypes
Package-based monorepo 8/10 (when justified) Multiple deployables, real shared packages Single app pretending it has packages
Clean / hexagonal everywhere 6.5/10 Complex regulated domains, integration-heavy services Most CRUD apps — pays ceremony tax for nothing
Flat by-type (components/, hooks/, services/, helpers/) 4/10 — anti-pattern Throwaway prototypes only Anything that ships

# Selection tree

Q1. Is this a throwaway prototype that won't ship?
   YES → flat or single-feature folder is fine; skip the rest of this guide.
   NO  → continue.

Q2. Multiple deployables (web + api + worker), or genuinely shared packages?
   YES → Package-based monorepo (apps/ + packages/). Choose Nx if AI/CI heavy, else Turborepo.
   NO  → continue.

Q3. Single app. Does the framework provide native routing/runtime conventions?
   YES → Framework-native shell + feature-first slices.
        For React+Vite: src/app/ (composition) + src/routes/ (pages) + src/features/ (slices) + src/shared/ (cross-cutting).
        For Next.js: src/app/ (router) + src/features/ (slices) + src/server/ (durable logic) + src/shared/.
        For Power Apps code app: src/{features,shared,services} — code app has no native router.
   NO  → fall back to plain vertical-slice with explicit feature folders.

Q4. Does the domain have hard business rules (regulated, money, compliance)?
   YES → Add hexagonal indirection inside affected slices ONLY (DDD score ≥10 → see ddd-tactical.md).
   NO  → keep slices light; no Repository<T> / UseCase / Mapper layers.

Q5. Is the frontend going to host >5 distinct domains (auth + billing + admin + reports + ...)?
   YES → Adopt FSD-light: layers (`app/`, `processes/`, `pages/`, `widgets/`, `features/`, `entities/`, `shared/`) with import direction enforced by lint.
   NO  → flat `features/` is enough.

# What "framework-native + feature-first" looks like

# React + Vite + TypeScript

src/
├─ app/                   # composition root: providers, router, theme, main.tsx
├─ routes/                # route-visible pages (one folder per page)
├─ features/              # reusable feature slices: auth/, billing/, profile/
│  └─ <feature>/
│     ├─ components/
│     ├─ hooks/
│     ├─ schemas/
│     ├─ services/        # or api/
│     └─ <feature>.test.ts
├─ shared/                # genuinely cross-feature: ui/, lib/, config/, types/
└─ test/                  # global setup, msw mocks

# Next.js App Router

src/
├─ app/                   # routes (Server Components by default), route groups, route.ts (thin)
├─ features/              # business slices reused across routes
├─ server/                # durable backend logic: db/, services/, repositories/, auth/
├─ shared/                # ui/, lib/, schemas/, config/

Rule: route.ts parses, validates, calls a service, responds. Domain logic lives in src/server/<area>/. 'use client' lives at the smallest interactive boundary — never at the top of a page.

# Power Apps code app (no native router)

src/
├─ features/<feature>/    # components, hooks, services
├─ shared/                # ui, lib, config
├─ services/              # generated Dataverse services
└─ models/                # generated TypeScript models

Code apps lack a router; App.tsx is the composition root. Feature-first still applies.

# Anti-patterns this catalog explicitly rejects

  • Flat by-type (components/, hooks/, services/, all parallel) — feature ownership is inferred from naming, agents waste tokens reconstructing it.
  • Business logic in route.ts / +page.server.ts / route handler — boundary files become 260-line hotspots. Move to server/ or feature service.
  • shared/utils/helpers/ dumping ground — anything reused by 1 caller doesn't belong in shared.
  • Premature monorepo — apps/web/ containing the entire app, packages/ empty or with one trivial config package. Wait until two real deployables.
  • Clean architecture in CRUD slices — UseCase + Repository + Mapper + DTO + Entity for a list-of-items page is overhead that buys nothing.
  • Shared package per slice — packages/auth-feature/, packages/billing-feature/ defeats locality; reuse-of-1 is not reuse.

# How this integrates with paliers

Palier Default pattern
0 → 1 BOOTSTRAP picks pattern at scaffolding time. Default: framework-native + feature-first. Recorded in .claude/.meta-govern.json.
1 → 2 Pattern stays. New features go in features/<new-feature>/ — never in a parallel by-type tree.
2 → 3 Multi-dev. eslint-plugin-boundaries becomes worth the setup (see tooling-architecture-checks.html).
3 → 4 CI. Architecture checks (Knip, dep-cruiser) wired into validate.
4 → 5 Dual-runtime. Pattern unchanged. AGENTS.md mirror added.
5 → 6 Mature. May extract real packages/ if reuse is now real.

# When BOOTSTRAP should ask the user

Don't ask:

  • Single app, no monorepo, framework detected → default to framework-native + feature-first silently.
  • Power Apps code app → feature-first silently.

Ask:

  • Two or more deployables detected (apps/ exists with >1 child) → confirm monorepo.
  • Domain looks regulated (DDD score ≥10) → confirm whether hexagonal indirection is wanted in core slices.

  • 5 distinct top-level domains hinted by spec → propose FSD-light.

Default lives in references/project-archetypes.html.

# Validation hooks

audit-project.mjs should warn (not block) on:

  • Top-level components/ AND hooks/ AND services/ parallel folders with >5 files each → flat by-type detected → SUGGEST migration.
  • route.ts or +server.ts >120 lines → boundary file owns logic → SUGGEST extraction.
  • shared/ containing >30 files → SUGGEST audit; "shared" should be small.
  • packages/ with only one package → SUGGEST collapsing back to single app.

These are advisory; the user decides.
