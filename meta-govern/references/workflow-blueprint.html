Workflow Blueprint — End-to-End Project Lifecycle

Source: synthesis of Temps Chantier's full workflow + Brillance Décor's brainstorm→write-plan→execute-plan→quality-gate sequence.

# The end-to-end lifecycle

A project bootstrapped by meta-govern follows this lifecycle:

PROJECT INIT
   ↓
BOOTSTRAP (meta-govern)
   - Sources of truth (3 docs)
   - .claude/ skeleton
   - 5 core skills, 4 core agents, 5 hooks, 8 rules
   - package.json scripts
   - .husky/pre-commit
   ↓
FEATURE WORK
   ↓
   /brainstorm "<topic>"               # design phase
      → docs/specs/YYYY-MM-DD-<topic>-design.md (with Source-of-truth delta block)
   ↓
   /write-plan                          # plan phase
      → docs/plans/YYYY-MM-DD-<topic>-plan.md (Task 1 = Apply delta)
      → Phase 0 right after Task 1 when the plan depends on third-party infra
        (human setup in one session + automated preflight, PASS/FAIL per item)
   ↓
   /execute-plan                        # execution phase
      - Gate: Phase 0 preflight full PASS before any dev-task dispatch
      - 3-tier classification (BATCH / STANDARD / RIGOROUS)
      - Pipeline Task List
      - Parallel groups via worktrees (palier 3+)
      - Per-task: implementer (or ui-implementer) → spec-reviewer + code-quality-reviewer (foreground) → fix/defer
      - Final phase: apply source-of-truth delta
      - Commit per task or per group based on tier
   ↓
   /quality-gate                        # FINAL SCAN before merge
      - Deterministic 12-check script
      - Architectural review
      - Severity gates (CRITICAL/HIGH/MEDIUM/LOW)
   ↓
COMMIT / MERGE / DEPLOY
   ↓
SESSION REVIEW (periodic)
   ↓
   /session-review                      # honest retrospective
      → 5 dimensions: self-eval/10, what worked, what poorly, agent/skill review, improvements
   ↓
   Append lessons to govern-claude/references/session-lessons.md
   ↓
GOVERNANCE CADENCE
   ↓
   Every 2-4 weeks:
      /govern-claude                    # project-level audit
         → drift detection, baseline diff, evolution suggestions
   ↓
   When meta-govern bumps:
      meta-govern AUDIT → migrate plan → MIGRATE
   ↓
   When triggers met:
      Promote to next palier

# Per-phase contracts

# Brainstorm phase (design)

Skill: brainstorm (or project-brainstorming)

HARD GATE: NO implementation until:

  1. Each section approved by user
  2. ## Source of truth delta block written

Output: docs/specs/YYYY-MM-DD-<topic>-design.md

Mandatory sections:

  • Context (why we're doing this)
  • Approach (architectural decisions)
  • Acceptance criteria — observable per-behavior pass/fail conditions (not a test strategy)
  • Twin-domain parity inventory — when the feature mirrors an established domain (internal↔external, a future module cloning a current one), classify each counterpart capability specified/adapted/excluded/MISSING before scoping
  • Source of truth delta — what changes in spec / data-model / catalog

Sub-agent: codebase-reality-check (mandatory pre-Step-1; verifies that referenced files/symbols actually exist)

Sub-agent: persona-simulator (mandatory between Sections 4 and 5; UX role-play with project-scoped personas)

# Write-plan phase

Skill: write-plan (or project-writing-plan)

HARD GATE: Rejects designs without ## Source of truth delta. Mandatory:

  1. Task 1 = "Apply source-of-truth delta"
  2. Decision Journal section
  3. Design→tasks coverage traceability — every design requirement maps to a task or an explicit out-of-scope (catches the silently-dropped-requirement class)
  4. Self-review (2 review passes — Track A spec + Track B codebase — both 0 issues)

Output: docs/plans/YYYY-MM-DD-<topic>-plan.md

Per-task structure:

  • Files (paths)
  • Agent assignment (implementer / ui-implementer / spec-reviewer / code-quality-reviewer)
  • Governing FUNC/RA/VAL/C-XX refs (traceability)
  • Acceptance criteria + edge cases as rendered checkboxes (not prose — prose AC fall out of the executable contract)
  • TDD checklist (RED → GREEN → REFACTOR)
  • Tier (BATCH / STANDARD / RIGOROUS)

# Phase 0 — human setup + automated preflight (autonomous-execution prerequisite)

When a plan is meant to execute autonomously but depends on third-party infrastructure (deployments, OAuth tenants, API keys, CLI access), the plan opens with a Phase 0, immediately after Task 1 (apply-delta):

  1. Human setup, one session — the user does ALL non-automatable third-party setup up front: create/confirm deployments, provision OAuth tenants, deposit API keys and service-account credentials, verify CLI access.
  2. Automated preflight — a script validates each access with a per-item PASS/FAIL verdict (deployment reachable, credentials valid, discovery endpoints resolvable, baseline validate green). Includes an env-parity item: the local env file (.env.local) carries every key the source actually reads (import.meta.env.* or equivalent) — a dev server handed to the owner for QA with missing env keys fails at first click, not at build.
  3. Gate — no development task starts before a full PASS. A FAIL item blocks execution and is surfaced to the user; it is never worked around.
  4. Residual human touchpoints — actions that cannot be front-loaded (write-freeze events, connector registrations, QA on a third-party account) are listed explicitly in the plan and scheduled — never discovered mid-plan. For a production cutover: no "go" until the tooling is committed, rehearsed on a non-prod target, and its guard-rails proven fail-closed.

Motivation: autonomous execution collapses into back-and-forth the moment a missing key or unreachable deployment surfaces mid-plan. Front-loading the human dependency is what makes the execution actually autonomous. Origin: personal-budget-app Convex-migration design (2026-07-01, §4.0 + AC-0); successor to the v1.4.0 pipeline lesson.

# Execute-plan phase

Skill: execute-plan (or project-subagent-driven-development)

3-tier classification:

  • BATCH: trivial mechanical changes (rename, format) → no per-task review
  • STANDARD: standard feature work → group-level review
  • RIGOROUS: complex / cross-cutting / risky → per-task review

Pipeline Task List: ordered task graph with dependencies as DAG. Parallel groups dispatch multiple implementers in same message.

Plan-content gate (before any classification or dispatch): assert each task is atomic, names its files, carries acceptance-criteria checkboxes, and is self-sufficient (a fresh subagent could execute it with no hidden context); plus the design→tasks coverage check. Bounce or split a task that fails — never dispatch a vague task verbatim (the implementer then guesses). This is a CONTENT gate, distinct from the structural "does the Execution Strategy block exist?" check.

Per-task discipline:

  1. Dispatch implementer (medium effort) with task spec
  2. Implementer reads canonical refs, writes failing test, implements, runs validate
  3. Implementer returns 7-section result summary
  4. Dispatch spec-reviewer AND code-quality-reviewer (high effort, plan mode, foreground in same message) — never background. Fresh-context verifier subagents outperform self-critique for verification (lesson v1.5.0, confirmed as Anthropic canon by the Claude 5 Workflow Playbook's self-verification guidance) — the implementer never reviews its own work.
  5. Reviewers return 3-section verdicts each (Findings / Notes / Verdict) — the finding stage is coverage-first (everything reported with confidence + severity); filtering happens at the verdict/disposition stage, never in the review prompt
  6. Disposition every finding: Fixed (re-run) or Deferred (new DEFERRED-XXX entry)
  7. Visual-QA gate (UI groups): a UI group is not "done" until its live render is verified, or the task is hard-tagged NEEDS_VISUAL_QA and BLOCKED. "Visual unverified" is not soft-disposable — jsdom/unit-green is blind to render. Real-boundary/integration checks (real datastore shape, not idealized mocks) are part of the same gate.
  8. Commit task or group

Final phase: Apply source-of-truth delta. Update docs/<spec>.md, docs/<data-model>.md, docs/<catalog>.md with the changes from the design.

# Quality-gate phase

Skill: quality-gate

Deterministic checks (script-based):

  1. Hardcoded colors (hex / rgba)
  2. i18n bypass (ternaries on language)
  3. File size > 300 lines
  4. any types
  5. console.log
  6. Secret patterns
  7. Direct fetch() in components
  8. Snapshot tests
  9. container.querySelector
  10. useEffect+setState heuristic
  11. TODO markers
  12. Project-specific (Dataverse FormattedValue, etc.)

Architectural review (manual):

  1. Duplication > threshold-of-three
  2. Prop drilling
  3. Missing tests
  4. Spec alignment

Severity gates: CRITICAL (blocks ship) / HIGH (resolve before merge) / MEDIUM (resolve in 1 sprint) / LOW (advisory)

# Session review phase

Skill: session-review (user-level)

5 dimensions:

  1. Self-evaluation /10 with concrete rationale
  2. What worked well (cited examples)
  3. What went poorly (cost analysis)
  4. Subagents/skills review (read .md, cross-reference observed usage)
  5. Improvement suggestions for workflow + next-gen models

Output: appends to govern-claude/references/session-lessons.md (project) AND to ~/.claude/skills/meta-govern/references/lessons-log.html (global, when generic).

# Governance cadence phase

Skill: govern-claude (project-level, scaffolded by meta-govern)

Triggers:

  • Periodic (2-4 weeks)
  • After major refactor / addition
  • Before milestone
  • When user says "drift" / "audit" / "what's missing"

Output: comparison against baseline; severity-tagged findings; proposed diffs.

Delegate to:

  • skill-creator for new skill authoring
  • create-subagent for new agent authoring
  • meta-govern AUDIT for full-project audit

# Cross-cutting principles

# Every artifact has 4 attributes

  1. Source (3 canonical docs are the source-of-truth; everything else routes against them)
  2. Owner (which artifact owns this rule? CLAUDE.md / rule / skill / agent / hook)
  3. Triggered by (when does it activate?)
  4. Enforced by (probabilistic skill activation? deterministic hook? both?)

# Always-grounded discipline

  • Never invent skills/agents/hooks the user hasn't approved
  • Never invent file paths, symbol names, function names
  • Read existing siblings before creating new files (govern-claude first principle: "Read at least one existing sibling before creating any new file.")
  • Use grep over inventories — "Inventories rot, grep stays fresh"

# Probabilistic vs deterministic layers

  • Skills: 50-84% reliability (use for guidance)
  • Hooks: 100% reliability (use for critical rules)
  • Subagents: 100% reliability when explicitly invoked (use for verbose specialist work)
  • CLAUDE.md: 70-85% reliability (use for identity + invariants)
  • Rules: 70-85% reliability (use for path-conditional conventions)

For critical rules, use hooks. Always.

# How meta-govern's output integrates

After meta-govern BOOTSTRAP completes a project, the user has:

my-project/
├── CLAUDE.md                       # ≤120 lines
├── HANDOFF.md                      # auto-generated by PreCompact
├── package.json                    # validate scripts
├── .husky/pre-commit               # 3-stage gate
├── .gitignore                      # excludes .claude/settings.local.json, .claude/tmp/
├── .claude/
│   ├── settings.json               # 3 hooks
│   ├── rules/                      # 8 path-scoped rules
│   ├── skills/                     # 5 core skills
│   ├── agents/                     # 4 core agents
│   ├── hooks/                      # 5 hooks + lib
│   ├── scripts/                    # file-size-guard + quality-checks/
│   └── tmp/                        # runtime state
├── docs/
│   ├── <project>-spec.md           # FUNC-XX, RA-XX, VAL-XX
│   ├── data-model.md               # schema, contracts
│   ├── composants/
│   │   └── catalogue-composants.md # C-XX
│   ├── architecture/
│   │   └── ddd-decision.md         # scorecard outcome
│   ├── specs/                      # design drafts (post-brainstorm)
│   ├── plans/                      # plans (post-write-plan)
│   ├── reports/                    # execution reports
│   └── backlog-deferred.md         # DEFERRED-XXX entries
└── (source code)

The first day of feature work, the user invokes /brainstorm and the lifecycle begins.

# Stack-specific deviations

# Power Platform (Code App + Dataverse)

  • Add add-dataverse, code-app-deploy, code-app-connect skills (these are USER-LEVEL — already global)
  • Add Dataverse-specific rules: data-layer.md references repository-per-table, OData safety, FormattedValue ban, column registry compliance
  • Add dataverse-audit skill at palier 2

# Convex

  • Add Convex skills (these come as a vendored bundle; user already has them)
  • Add convex-component-auditor agent at palier 2 (per-component verification)
  • Backend rules: data-layer.md references Convex hooks only, ConvexError codes, schema in convex/schema.ts

# Vite + React + TypeScript

  • Add vite-react-ts-setup skill at BOOTSTRAP (user already has globally)
  • Standard: ESLint 9 flat config, Vitest 4, Tailwind 3-4

# Cloudflare Workers

  • Add cloudflare-* skills (workers-best-practices, durable-objects, etc.) — already in plugin
  • Env vars in git-integrated Workers Builds: VITE_* vars are build-time only, and the build runners never see a gitignored .env.local. Build-time env is configured per trigger via the Workers Builds REST API (or dashboard) — Preview and Production are SEPARATE triggers, not a toggle on one config.
  • wrangler has ZERO Workers Builds commands (no builds/ci subcommand). Use the REST API directly (accounts/{id}/builds/...) with a scoped API token (Workers Builds Configuration:Edit + Workers Scripts:Read) — not OAuth/wrangler login.
  • The Builds API keys on the worker's tag UUID, not its name. GET /accounts/{id}/workers/scripts returns both id (human name) and tag (UUID); /builds/workers/{worker_tag}/triggers wants the tag. Passing the name silently returns result: [] with success:true — easy to misread as "no triggers configured".
