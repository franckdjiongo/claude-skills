DDD — Tactical Patterns (Quick Reference)

This reference is a quick map. For full guidance, invoke the existing master skill domain-driven-design.

# When to apply

  • DDD score ≥ 10 (per ddd-scorecard.html)
  • Strategic artifacts (glossary, context map, BC canvas) exist
  • Domain has rich invariants (state machines, transactions, refunds)

# NOT when to apply

  • DDD score < 10 → use Transaction Script / Active Record
  • "DDD-Lite" warning: applying tactical patterns without strategic work is WORSE than not doing DDD at all

# The 7 tactical patterns

# 1. Value Object

  • Defined by attributes (no identity)
  • Immutable
  • Structurally equal (two instances with same attributes are interchangeable)
  • Promoted from primitives that recur (Email, Money, PhoneNumber)
class Email {
  private readonly value: string;
  private constructor(value: string) {
    if (!isValidEmail(value)) throw new InvalidEmail();
    this.value = value;
  }
  static of(value: string): Email { return new Email(value); }
  toString(): string { return this.value; }
  equals(other: Email): boolean { return this.value === other.value; }
}

Vernon's bias: "When in doubt, start as a Value Object; promote to Entity only when identity is required."

# 2. Entity

  • Has identity that persists across state changes
  • Mutable (within invariants)
  • Equality by ID, not attributes
class Order {
  readonly id: OrderId;
  private status: OrderStatus;
  // ... invariant-protecting methods only; no public setters
}

# 3. Aggregate

  • Cluster of entities + value objects with one Aggregate Root
  • Transactional consistency boundary
  • Other aggregates referenced by ID only (NEVER by navigation)
  • One aggregate per transaction (Vernon's #1 tactical rule)
class Order {  // Aggregate Root
  private items: OrderItem[];
  // OrderItem is internal — never exposed; modifications only via Order's methods
  addItem(sku: SKU, quantity: number): void {
    if (this.status !== 'draft') throw new CannotModifyShippedOrder();
    // ... invariant: at most 100 items per order
  }
}

# 4. Domain Event

  • A thing that happened in the domain (past tense: OrderShipped, not ShipOrder)
  • In-process inside a BC
  • Schema owned by the BC
  • May be sync or async

Distinct from Integration Event:

  • Integration events cross BCs
  • Stable versioned public contract
  • Async via broker
  • At-least-once delivery

# 5. Repository

  • Interface in domain layer
  • Implementation in infrastructure layer
  • One repository per Aggregate Root (NOT per entity, NOT per table)
  • Methods named in ubiquitous language (findOverdue(), save(), ofId())
  • Returns fully-valid aggregates only (no IQueryable leakage)
interface OrderRepository {
  ofId(id: OrderId): Promise<Order | null>;
  save(order: Order): Promise<void>;
  findOverdue(): Promise<Order[]>;
}

ANTI-PATTERN: IRepository<T> (generic) — leaky, becomes CRUD wrapper.

# 6. Domain Service

  • For domain logic that doesn't naturally belong to one entity
  • Example: PricingService.calculate(order, customer, discounts) — needs multiple aggregates
  • Stateless
  • Lives in domain layer

NOT to be confused with Application Service (use case orchestrator) or Infrastructure Service (technical concern).

# 7. Process Manager / Saga

  • Orchestrates long-running multi-aggregate workflows
  • Uses domain events as triggers
  • Manages compensating transactions (refund on failed shipment)
  • Stateful (tracks where it is in the process)

In Power Platform: Power Automate flows are process managers. NOT domain. Keep them thin; delegate decisions to domain code.

# The 4 rules of Aggregate Design (Vernon)

  1. Model true invariants in consistency boundaries
  2. Design SMALL aggregates
  3. Reference other aggregates by IDENTITY only
  4. Use eventual consistency between aggregates

# Outbox Pattern (mandatory for events)

Avoids double-write problem. Insert outbox row in same DB transaction as the aggregate save:

BEGIN TRANSACTION;
  UPDATE orders SET status='shipped' WHERE id=@id;
  INSERT INTO outbox (event_id, type, payload, dispatched) VALUES (uuid(), 'OrderShipped', '{...}', false);
COMMIT;

Separate dispatcher polls outbox, publishes to broker, marks dispatched. Consumers deduplicate via event_id (inbox pattern).

# TypeScript-first DDD

  • Strict mode mandatory
  • readonly everywhere by default
  • Private constructors with static factories
  • Branded types for IDs:
    type OrderId = string & { __brand: 'OrderId' };
function OrderId(value: string): OrderId {
  return value as OrderId;
}
  • Result<T, E> for fallible operations
  • ORM (Prisma / Drizzle) lives OUTSIDE the domain (in infrastructure adapter)
  • In-memory repositories for tests

# Power Platform tactical mapping

  • C# plugin = Aggregate behavior holder (sandboxed transaction = aggregate transaction)
  • Plugins should be THIN: delegate to pure domain classes
  • Mapper-as-ACL pattern: NEVER let Dataverse types (@odata.bind, _value, FormattedValue) into domain
  • Keep Mapper class at the domain boundary

# When meta-govern installs DDD tactical scaffolding

In BOOTSTRAP, if DDD score ≥ 10:

  • src/<feature>/<domain>/ folder structure (one per Aggregate Root)
  • .claude/rules/ddd-tactical.html (path-scoped to src/**/*.ts)
  • .claude/hooks/ddd-anti-pattern-guard.mjs (blocks: IRepository<T>, public setters on aggregates, ORM types in domain)
  • ESLint rule additions
  • TypeScript path mappings

# Anti-pattern detection (scripts/audit-project.mjs)

When DDD score ≥ 10, these checks run:

  1. Anemic detection: aggregate roots with public setters and no methods
  2. IRepository<T> generic (leaky)
  3. ORM types in domain layer (DbContext, Entity attribute imports in domain/)
  4. Primitive obsession: command parameters all strings/numbers
  5. Mutable collections returned from aggregates
  6. Present-tense events (UpdateOrder vs OrderShipped)
  7. Property-only tests (no behavior assertions)

Findings emit HIGH severity for IRepository, MEDIUM for primitive obsession.
