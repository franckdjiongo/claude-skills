Engineering Principles — The User's Canon

The user's foundational engineering principles. Applied across every project. Encoded in templates/rules/clean-code.md.tpl, embedded in agent bodies, enforced via code-quality-reviewer.

# DRY — Don't Repeat Yourself (threshold of three)

Three identical fragments → extract. NOT two. Premature DRY produces wrong abstractions; lived duplication reveals the right shape.

1 occurrence  → write it
2 occurrences → leave it (might diverge)
3 occurrences → extract (pattern is real)

If extraction reveals the second occurrence diverged: the abstraction was wrong. Inline it back.

# KISS — Keep It Simple, Stupid

Simplest code that satisfies the spec. Not the cleverest. Not the most extensible. The simplest.

A new reader should grasp the function in 30 seconds. If they need a comment to understand WHAT, the code is too clever.

# YAGNI — You Aren't Gonna Need It

Don't build for hypothetical future requirements. Build for the current spec.

Three lines of repetition is BETTER than a premature abstraction.

When you genuinely need the abstraction, you'll have 3 concrete examples to derive it from. Premature abstraction has only one example — and it's wrong.

# SOLID — pragmatic interpretation

  • Single Responsibility: a function/class does one thing well
  • Open-Closed: add behavior via composition, not modification
  • Liskov: subtypes don't break parent contracts
  • Interface Segregation: don't force consumers to depend on what they don't use
  • Dependency Inversion: depend on abstractions; inject implementations

Don't over-apply. Most YAGNI violations are SOLID over-application.

# SINE — Single side-effect, In, Named, Explicit

The user's own framing for side-effect discipline:

  • Single: a function has one side effect (or zero, or one composed family)
  • In: side effect is at the boundary (top of call stack, not buried)
  • Named: the side effect is in the function name (saveOrder, not processOrder)
  • Explicit: the side effect is documented (return type, JSDoc, or type system)

Pure functions everywhere except the boundary. Boundaries are explicit.

# Meaningful names

Names reveal intent. The reader shouldn't need to read the implementation to understand the name.

// Bad
const d = 30;
function fn(x, y) { return x.filter(z => z.s > y); }

// Good
const TRIAL_DURATION_DAYS = 30;
function ordersAboveThreshold(orders, threshold) { return orders.filter(o => o.subtotal > threshold); }

# Small functions

Functions ≤ 30 lines (target: 10-20). One screen. Larger → extract.

A 200-line function is a smell. A 500-line function is debt.

# Comments explain WHY, not WHAT

Code says WHAT. Comments say WHY (the surprise, the constraint, the reason).

// Bad: comment restates the code
i++; // increment i

// Good: comment explains the surprise
i++; // skip the BOM marker on UTF-8 input

If you remove the comment and the reader can't infer the WHY → the comment was load-bearing. Keep it.

If removing the comment changes nothing → delete it.

# Fail fast

Validate early. Crash visibly. Don't swallow errors.

// Bad: silent fallback
function getUser(id) {
  return users.find(u => u.id === id) || {};
}

// Good: fail fast
function getUser(id) {
  const user = users.find(u => u.id === id);
  if (!user) throw new UserNotFound(id);
  return user;
}

# Boy Scout Rule

Leave the codebase cleaner than you found it. Not "perfect" — just incrementally better.

When fixing a bug, also: fix a typo, rename an unclear variable, extract a duplicated block, delete dead code. Three small improvements per touched file.

Compounds over time. The codebase tends toward clean.

# Tests as documentation

Tests are the most reliable docs. They're executable; they don't lie.

class OrderTest {
  it('rejects orders with negative quantities')
  it('charges shipping when subtotal < $50')
  it('rounds prices to 2 decimal places')
}

A new dev reads these and learns the contract.

# When principles conflict

Order of precedence:

  1. YAGNI wins over DRY — premature DRY is worse than three concrete copies
  2. KISS wins over SOLID — premature abstraction is worse than simple repetition
  3. Explicit wins over terse — verbose-but-clear beats terse-but-cryptic
  4. Behavior contract wins over internal structure — the test of the contract is sacred; refactor the structure freely

# Anti-patterns this canon blocks

  • Anemic objects: data bags with no behavior (violates Single Responsibility)
  • God functions: 300+ lines doing 5 things (violates Small Functions)
  • Premature abstraction: extracting a base class with one subclass (violates YAGNI + DRY threshold)
  • Defensive null-everywhere: every function checks input is non-null (violates Fail Fast)
  • Cleverness for show: ternary chains, regex magic, one-liners (violates KISS)
  • Comment-restates-code: line-by-line comments saying what the code already says
  • Silent error swallowing: try/catch + return null/empty (violates Fail Fast)
