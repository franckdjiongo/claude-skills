Hooks — Canonical Patterns

Source: Progressive Context Disclosure for Claude Code on Windows.md, Claude Code Architecture Research.md, observed patterns in Temps Chantier (11 hooks) and Brillance Décor (3 hooks).

# What hooks are

Hooks are deterministic enforcement layers. They run outside the LLM loop. They have:

  • Zero standing-context cost
  • 100% reliability (run on every event)
  • The power to BLOCK Claude's actions

Skills teach. Hooks enforce. Never substitute one for the other.

# The 22 hook events

# Session lifecycle

  • SessionStart — fires once when session begins
  • SessionEnd — fires when session terminates

# Conversation

  • UserPromptSubmit — fires before Claude sees user prompt
  • Stop — fires before Claude finalizes assistant turn

# Tool use

  • PreToolUse — before any tool call (filterable by tool name)
  • PostToolUse — after successful tool call
  • PostToolUseFailure — after failed tool call

# Subagent

  • SubagentStart — when a subagent is dispatched
  • SubagentStop — when a subagent returns

# Context

  • PreCompact — before context compaction
  • PostCompact — after context compaction (re-injection point)
  • InstructionsLoaded — after CLAUDE.md / instructions are loaded
  • ConfigChange — settings.json change detected

# Infrastructure

  • WorktreeCreated / WorktreeDestroyed — worktree lifecycle
  • NotificationDisplay — push notifications
  • ElicitationRequested — user input requested

# Handler types

A hook handler can be one of four:

# 1. Command (shell, exit-code-driven)

Most common. Hook script runs as a subprocess, exit code drives action.

{
  "PreToolUse": [
    {
      "matcher": "Edit|Write|MultiEdit",
      "hooks": [
        {
          "type": "command",
          "command": "node ${CLAUDE_PROJECT_DIR}/.claude/hooks/validate-plan.mjs"
        }
      ]
    }
  ]
}

Bash blind spot — an Edit|Write|MultiEdit matcher only sees the Edit/Write/MultiEdit tools. A write routed through the shell (heredoc cat > f <<EOF, sed -i, tee, node -e) bypasses these guards entirely — it arrives as a Bash call. The bash-write-guard (PreToolUse Bash, below) covers that vector.

Exit code semantics (for command hooks):

  • 0 — allow (silent)
  • 1 — soft block: emit reason, continue
  • 2 — hard block: emit reason, halt operation

# 2. HTTP (POST to URL)

Less common. Hook posts JSON to URL, awaits response.

# 3. Prompt (single-turn fast Claude)

For light reasoning (e.g., classify a commit message).

# 4. Agent (multi-step subagent verification)

For heavy verification (run tests, parse output, decide). Use context: fork to avoid main-thread bloat.

# Hook script — JSON I/O contract

All hook scripts read JSON from stdin and write JSON to stdout.

# Input shape (varies by event)

For PreToolUse:

{
  "session_id": "abc",
  "tool_name": "Edit",
  "tool_input": {
    "file_path": "/path/to/file",
    "old_string": "...",
    "new_string": "..."
  },
  "prompt": "...",
  "transcript_path": "...",
  "cwd": "/path/to/project"
}

For Stop:

{
  "session_id": "abc",
  "last_assistant_message": "...",
  "transcript_path": "...",
  "cwd": "/path/to/project"
}

# Output shape (for command hooks)

{
  "decision": "allow" | "block",
  "reason": "...",
  "additionalContext": "..."   // optional, prepended to next assistant turn
}

If the script just exits 0 with no JSON → silently allow.

# macOS Apple Silicon hardening (CRITICAL)

#!/usr/bin/env node
// .claude/hooks/my-hook.mjs

const PATH_PREFIX = "/opt/homebrew/bin:/usr/local/bin:/opt/homebrew/sbin:/usr/sbin:/usr/bin:/sbin:/bin";
process.env.PATH = `${PATH_PREFIX}:${process.env.PATH || ""}`;

Without explicit PATH:

  • node, git, bun, rg not found on Apple Silicon
  • Hook fails silently
  • Whole event handler breaks

Other macOS gotchas:

  • Don't use nvm — hook environment is non-interactive, no nvm init
  • Use #!/usr/bin/env node not #!/usr/local/bin/node (path differs)
  • ~/.zshrc and ~/.profile MUST be silent at startup (no echo/printf) — output corrupts JSON

# Standard hook set (BOOTSTRAP installs)

# track-workflow.mjs (PostToolUse Edit|Write|MultiEdit|Bash)

Records timestamps for last feature-file edit & last validate-style command into
.claude/tmp/workflow-state.json. Used by enforce-workflow.mjs.

# enforce-workflow.mjs (Stop)

Reads workflow-state.json. If lastEdit > lastValidate AND last assistant message
contains completion-style words — bilingual EN/FR ("done", "completed", "ready",
"finished" / "terminé", "complété", "prêt", "fini") — returns
{decision: "block", reason: "Run `bun run validate` before ending session"}.
Batch sentinel: while .claude/tmp/.batch-in-flight has an mtime younger than
SENTINEL_TTL_MS (30 min), the block downgrades to a logged warning — bounded
fail-open; an abandoned sentinel expires and the gate resumes (v1.11.0).

# precompact-handoff.mjs (PreCompact)

Generates HANDOFF.md with: branch, modified files (top 40), active plans,
latest design, resume instructions, discipline reminders. Saves to project root.

# postcompact-reinject.mjs (PostCompact)

Detects plan-execution context (HANDOFF.md content + branch name `plan/` prefix
+ scans for plans with unchecked Pipeline). Re-injects 5-rule discipline summary
as `additionalContext`.

# session-start-env-check.mjs (SessionStart)

On Apple Silicon: verifies node, git, bun, rg in PATH. Reports missing tools
to additionalContext. Cached: skips if checked < 24h ago (.claude/tmp/last-env-check.json).

# Higher-palier hooks (Palier 3+)

# subagent-plan-edit-guard.mjs (PreToolUse Edit|MultiEdit, scoped to implementer agents via frontmatter hooks:)

Blocks edits to plan files (docs/plans/**/*.md) by implementer agents.
Plans are managed by orchestrator only.

# agent-dispatch-preflight.mjs (PreToolUse Agent)

Poses/refreshes the batch sentinel .claude/tmp/.batch-in-flight when a WRITING
subagent (subagent_type implementer | ui-implementer) is dispatched — the
deterministic backstop of execute-plan 4a's prose-level posing (v1.10.0
incident: a serial writing dispatch without the sentinel false-tripped the
Stop gate). Reader dispatches (reviewers, persona-simulator) pose nothing.
Fail-open by construction: no deny/block code path, every branch exits 0,
all fs ops in try/catch. The consumer (enforce-workflow) bounds the window
with a 30-min mtime-TTL; the poser refreshes mtime on every writing dispatch
— producer and consumer agree on mtime semantics. Template since v1.11.0
(templates/hooks/agent-dispatch-preflight.mjs.tpl, wired in settings.json.tpl
behind IF_PALIER_GTE_3). Repurposed name: the earlier file-size-warning idea
documented here was never built and is redundant with file-size-growth-guard.

# daily-drift-alert.mjs (SessionStart)

Once per 24h: runs quality-checks.js --scope full --fail-level critical. Reports
oversized files + architecture drift (folders not mentioned in context-map.md).
Silent when clean.

# validate-plan.mjs (PreToolUse Write|Edit|MultiEdit)

Blocks edits on plans-with-tasks-but-no-Execution-Strategy that mutate checkboxes.
Forces /execute-plan.

# plan-closeout-guard.mjs (PreToolUse Write|Edit|MultiEdit — palier ≥2)

Simulates the incoming edit on docs/plans/**/*.html. Blocks when it INTRODUCES a
plan-task section that is data-status="done" while still holding unchecked
detail checkboxes without a PENDING-MANUAL marker (premature close-out).
Diff-scoped (pre-existing violations never trip unrelated edits); fail-open.
PreToolUse, not PostToolUse: after the tool ran, the bad edit has already landed.
Origin: personal-budget-app 2026-07-02 — T10-14 marked done with 0 detail boxes checked.

Bash blind spot — these three guards (subagent-plan-edit-guard, validate-plan, plan-closeout-guard) filter Edit|Write|MultiEdit, so an equivalent write launched through the shell (heredoc, sed -i, tee, node -e) escapes them. The bash-write-guard below closes that vector.

# file-size-growth-guard.mjs (pre-commit hook, NOT in settings.json — wired via .husky/pre-commit)

Blocks commits that GROW an already-over-budget file. Grandfathers legacy debt.
SIZE_ALLOWLIST exempts specific files.

# bash-write-guard.mjs (PreToolUse Bash)

The Edit|Write|MultiEdit matchers above never see a write routed through the shell. bash-write-guard closes that blind spot: it inspects the Bash command string, extracts every write target, and applies the same doctrine the file guards apply to their tool inputs.

Detection is delegated to a pure lib, detectWriteTargets(command) (.claude/hooks/lib/bash-write-detect.mjs), which returns { path, vector }[]. Vectors covered:

  • redirect — > f / >> f
  • heredoc — cat > f <<EOF
  • tee — tee [-a] f
  • sed-i / perl-i — in-place edits
  • node-e / python-c — inline scripts calling writeFileSync / createWriteStream / open(...,"w")
  • cp / mv / touch — file materialisation
  • git-add-all — git add -A / git add . (path .)

The lib stays pure: it returns [] when nothing is detected or a parse is impossible, splits the command on && / || / ; / | (quote-aware, best-effort — not a real shell parser), and excludes /dev/null. Normalising a target to a repo-relative path is the hook's job, not the lib's.

# Decision contract

  • DENY (holds even without the enforce env): a target under {{DOCS_ROOT}}/…*.md (canonicalised, symlinks resolved, reusing the block-docs-markdown allowlist so a legitimately-authored .md is not denied); OR a protected project path; OR git add -A / git add ..
  • SHADOW-LOG (default — observes without denying): a target under src/** appends one JSONL line { ts, command, target, vector, mode:"shadow" } to .claude/tmp/bash-write-guard.log, then exits 0. Promoted to DENY when BASH_WRITE_GUARD_ENFORCE=1.
  • ALLOW: scratchpad/, .claude/tmp/, coverage/, node_modules/, /dev/null, and any command with no detected write target.

Shadow mode is the general observe→enforce pattern: <GUARD>_ENFORCE=1 promotes logging to blocking, so the guard rolls out silently, its log gets reviewed, then it flips to a hard block once its false-positive rate is known.

Fail-open by construction: stdin on fd0 is read in a try/catch, every parse is guarded, and each branch — error branches included — exits 0 without a deny. A guard that crashes leaves the action untouched. The DENY shape follows the standard PreToolUse contract (permissionDecision:"deny" plus a permissionDecisionReason); an ALLOW emits nothing.

# Hook lib pattern

For multiple hooks sharing logic, use a shared library:

.claude/hooks/
├── lib/
│   ├── hook-utils.mjs          # Shared helpers
│   └── hook-utils.d.mts        # TypeScript types
├── enforce-workflow.mjs        # imports from lib
├── track-workflow.mjs          # imports from lib
└── ...

hook-utils.mjs exports:

  • projectDir() — $CLAUDE_PROJECT_DIR or fallback to cwd
  • readJsonStdin() / writeJsonStdout()
  • reduceWorkflowState() — pure reducer for tracking
  • shouldBlockOnStop() — completion-message regex match
  • isFeatureFile() / isValidateBash() — classifier helpers
  • buildHandoffMarkdown() — handoff template
  • analyzePlanToolUse() — plan-edit detection

# Cost-efficient hook design

# Don't dump logs into context

Bad:

console.log(`Found ${issues.length} issues:`);
issues.forEach(issue => console.log(`  - ${issue}`));
process.exit(2);  // block

Good:

// Write details to file
fs.writeFileSync('.claude/tmp/last-hook-output.json', JSON.stringify({issues}));

// Return one-line pointer in JSON
process.stdout.write(JSON.stringify({
  decision: 'block',
  reason: `${issues.length} issues; see .claude/tmp/last-hook-output.json`
}));

# Use context: fork for verbose verification

If a hook handler is an agent that runs tests:

{
  "Stop": [
    {
      "hooks": [
        {
          "type": "agent",
          "agent": "test-runner",
          "context": "fork"
        }
      ]
    }
  ]
}

The agent runs in a fork; main thread sees only summary.

# Dispatch loop & decision contract

hook script reads stdin
   ↓
hook script does work (file checks, regex, validation)
   ↓
hook script writes JSON to stdout (or just exits 0 silent)
   ↓
Claude Code applies decision:
   - decision: "allow" or no JSON → continue
   - decision: "block" → halt operation, surface reason to user
   - additionalContext present → prepend to next assistant turn
   ↓
Hook process exits with appropriate code

# Invariants

  • Hooks must complete in <2s (timeout default; some events have lower)
  • Hooks must be deterministic (same input → same output)
  • Hooks must not require interactive input (no TTY)
  • Hooks must not modify user files unless explicitly designed to (e.g., format-on-edit)
  • Every hook / guard ships its simulation or test in the same commit — a broken guard fails silently (exit 0, blocks nothing), so an unexercised guard is not proven infrastructure. Project-authored guards without an associated test are flagged by audit-project.mjs (area hook-tests, v1.12.0)
  • Zero orphan hook on disk: every .claude/hooks/*.mjs (excluding lib/ and *.test.mjs) is wired in settings.json or an agent frontmatter hooks:. The disk→settings direction is proven by hooks-inventory.test.mjs; a hook present on disk but referenced nowhere runs never
  • A guard's test exercises both directions — a positive case (the forbidden write is denied) and a negative case (a legitimate write passes). A guard proven only on its deny path can silently over-block a legitimate action
  • Hook tests spawn the real hook as a subprocess and feed it a JSON event on stdin (the runHook harness in hook-test-util.mjs), so the actual stdin/stdout contract is exercised rather than an imported function — the same path Claude Code uses at runtime
