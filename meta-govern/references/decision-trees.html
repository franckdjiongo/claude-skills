Decision Trees — Quick Decisions

Reference for fast routing during BOOTSTRAP, AUDIT, MIGRATE, ADVISE.

# 1. Where does this rule belong?

Rule: ___________________________________________

Q1. Must it be 100% enforced (zero tolerance for skipping)?
   YES → HOOK. Stop here.
   NO  → continue

Q2. Is it path/file-type specific?
   YES → .claude/rules/<name>.md with `paths:` frontmatter. Stop here.
   NO  → continue

Q3. Is it a multi-step workflow with domain knowledge?
   YES → Skill. Continue with Q3a:
       Q3a. Workflow has side effects (deploys, schema mutations)?
            YES → frontmatter `disable-model-invocation: true` (manual only).
            NO  → standard skill, ensure trigger phrases in description.
   NO  → continue

Q4. Always-on identity / source-of-truth pointer / model+effort default?
   YES → CLAUDE.md (≤120 lines budget; if budget exceeded, move oldest item out)
   NO  → continue

Q5. Verbose specialist work that should not pollute main context?
   YES → Subagent
   NO  → continue

Q6. External system (Notion / Vercel / GitHub / Convex)?
   YES → MCP server
   NO  → re-evaluate; the rule may not need a primitive at all (could be tribal knowledge / a comment in code)

# 2. Should this project use DDD?

See ddd-scorecard.html for the full 8-item scorecard. Quick gate:

Score ≥ 10 → Full DDD: bounded context canvas, glossary, aggregate-per-AR repos, anti-pattern hooks
Score 5-9 → Strategic DDD only: glossary + context map; tactical patterns optional
Score < 5 → Transaction Script / Active Record. Don't force DDD.

Most Power Apps code apps and small SPAs land at <5 or 5-9. Don't over-engineer.

# 2.5 Architecture pattern selection

Source: architecture-patterns.html. Use during BOOTSTRAP step 4b.

Q1. Is this a throwaway prototype that won't ship?
   YES → flat or single-feature folder. Skip the rest.
   NO  → continue.

Q2. Multiple deployables OR genuinely shared packages?
   YES → Package-based monorepo (apps/ + packages/). Pick Nx if AI/CI heavy, else Turborepo.
   NO  → continue.

Q3. Single app — does the framework provide native routing/runtime conventions?
   YES → Framework-native shell + feature-first slices.
        React+Vite → src/app/ + src/routes/ + src/features/ + src/shared/
        Next.js   → src/app/ (router) + src/features/ + src/server/ + src/shared/
        Power Apps code app → src/{features,shared,services,models}
   NO  → fall back to plain vertical-slice with explicit feature folders.

Q4. Hard business rules (regulated, money, compliance)?
   YES → add hexagonal indirection inside affected slices ONLY (DDD score ≥10).
   NO  → keep slices light; no Repository<T>/UseCase/Mapper layers.

Q5. >5 distinct top-level domains hinted by spec?
   YES → adopt FSD-light (layers + import-direction lint).
   NO  → flat features/ is enough.

Default for most projects: framework-native + feature-first. Record decision in .claude/.meta-govern.json under architecturePattern.

# 3. Skill vs Subagent

"I need Claude to handle <task>."

Q1. Should the *current* context be teaching/doing it?
   YES → Skill (current context learns the workflow)
   NO  → Subagent (delegate to fresh context, get summary back)

Q2. Will it produce verbose output that would flood the main thread?
   YES → Subagent (or skill with `context: fork`)
   NO  → Skill is fine

Q3. Is it a one-shot job vs. a recurring workflow?
   ONE-SHOT → maybe just inline the prompt; don't create a primitive
   RECURRING → Skill or subagent based on Q1, Q2

Q4. Does it need to invoke other skills?
   YES → Skill (subagents don't auto-inherit skills; isolation forced)
   NO  → either works; pick by Q1, Q2

# 4. Skill's disable-model-invocation setting

Q. Does the skill have side effects (deploys, schema mutations, payments, sends emails)?
   YES → disable-model-invocation: true (only manually invoked)
   NO  → omit (default false; auto-invoke allowed)

Q. Is the skill triggered by 1-2 specific commands and never useful elsewhere?
   YES → consider disable-model-invocation: true (cleaner)
   NO  → leave default

# 5. Skill's context: fork setting

Q. Does the skill produce verbose tool output that would flood the main thread?
   YES → context: fork (skill body becomes prompt to fresh subagent)
   NO  → omit (default: runs in main context)

Q. Does the skill perform heavy validation (lint, audit, compliance)?
   YES → context: fork
   NO  → omit

Q. Will the skill's output be referenced later in the session?
   YES → don't fork (you need it in main context)
   NO  → fork is fine

# 6. Hook handler type

Q1. Is it a deterministic check answerable from filesystem state in <100ms?
   YES → command (shell exit-code)

Q2. Does it need to call out to a service (validation API, secrets server)?
   YES → HTTP (POST to URL)

Q3. Does it need light reasoning (e.g., classify a commit message)?
   YES → prompt (single-turn fast Claude)

Q4. Does it need multi-step verification (run tests, parse output, decide)?
   YES → agent (multi-step subagent)

# 7. Compact vs Clear vs Rewind

Context still relevant but window full?
   → /compact (focused: /compact <topic to keep>)

Context poisoned (wrong direction, hallucinated state)?
   → /clear

Want to rewind to a specific moment?
   → /rewind (visual UI; pick the turn)

Want to keep just a summary?
   → "summarize from here, then I'll /clear"

# 8. Bounded Context vs Microservice

Q. Does this slice have a single ubiquitous language?
   NO → keep splitting; you have multiple BCs masquerading as one
   YES → it's a Bounded Context

Q. Does it deserve its own deployable + database?
   YES → it can also be a microservice
   NO  → it's a BC inside a modular monolith (preferred default)

Khononov: "All microservices are bounded contexts, but not all bounded contexts are microservices."

# 9. Domain Event vs Integration Event

Q. Will the consumer live inside the same Bounded Context?
   YES → Domain Event (in-process, may be sync or async, schema owned by BC)
   NO  → Integration Event (cross-BC, async via broker, stable versioned contract, at-least-once)

# 10. Entity vs Value Object

Q. Does the object's identity persist across state changes?
   YES → Entity
   NO  → continue

Q. Are two instances with the same attributes interchangeable?
   YES → Value Object
   NO  → Entity (your invariants depend on identity)

Vernon's bias: "When in doubt, start as a Value Object; promote to Entity only when identity is required."

# 11. When to AUDIT (vs MIGRATE vs ADVISE)

Q1. Is meta-govern's version newer than the project's recorded version?
   YES → MIGRATE candidate. Run AUDIT first to decide.
   NO  → continue

Q2. Has it been >4 weeks since last AUDIT?
   YES → AUDIT now.
   NO  → continue

Q3. Did the user just complete a milestone (feature ship, refactor, model upgrade)?
   YES → AUDIT now.
   NO  → ADVISE only.

# 12. Promote to next palier?

See evolution-roadmap.html for full triggers. Quick gate per palier:

Palier 0 → 1: BOOTSTRAP signals: project has CLAUDE.md? .claude/settings.json? 5 core skills? 4 core agents?
Palier 1 → 2: ≥30 FUNC IDs OR project has live users
Palier 2 → 3: 2+ devs OR worktree workflow needed
Palier 3 → 4: PR opened on remote (GitHub/GitLab) OR CI requested
Palier 4 → 5: Codex/Claude.ai dual-runtime needed (e.g., for non-MCP integrations)
Palier 5 → 6: 30+ DEFERRED entries in backlog

# 13. When to refactor a CLAUDE.md

Q1. Is CLAUDE.md > 120 lines?
   YES → refactor.

Q2. Does CLAUDE.md contain `@filename` imports?
   YES → refactor; replace with declarative pointers.

Q3. Does it have defensive scaffolding ("MUST", "ALWAYS", "verify before returning")?
   YES → refactor; rewrite without defensive language.

Q4. Does it duplicate content also in .claude/rules/*.md?
   YES → refactor; pick one home (rules dir for path-conditional, CLAUDE.md for always-on identity).

Q5. Does it have file-type procedures?
   YES → refactor; move to .claude/rules/<file-type>.md with `paths:`.

If any → invoke claude-md-improver (plugin) for the surgical edit; meta-govern handles the surrounding decisions.

# 14. Adding new lesson to lessons-log

Lesson observed: ___________________________________________

Q. Is it generic across projects?
   YES → meta-govern lessons-log.md AND propose update to a reference
   NO  → project-level govern-claude session-lessons.md

Q. Does it require new template / new sub-agent?
   YES → propose new artifact in EVOLVE mode
   NO  → just append to lessons-log

Q. Does it invalidate an existing template?
   YES → bump meta-govern major version + MIGRATE all projects
   NO  → minor version bump
