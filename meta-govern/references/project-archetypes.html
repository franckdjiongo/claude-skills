Project Archetypes — Initial-Scaffold Profiles

Source: synthesis of LLM-friendly project architecture for AI coding agents in 2026.md plus existing palier system.

# Why this exists

Palier = maturity stage (0 → 6). Archetype = project's kind. The two are orthogonal.

A throwaway prototype can be palier 1; a production SaaS can also be palier 1 the day it bootstraps. They start with different scaffolds. Archetype shapes the initial palier-1 install; palier promotion adds capability over time.

# The four archetypes

# Archetype A — Small prototype

What it is: demo, spike, weekend hack, "is this idea worth pursuing", internal one-off.

Indicators: LOC < 500 expected, single dev, no live users planned, deployment optional.

Default scaffold (palier-1 minus):

  • Framework-native single app
  • Feature-first slices
  • CLAUDE.md (≤120 lines)
  • 5 core skills, 4 core agents, 5 hooks, 8 rules — full palier 1
  • ONE source-of-truth doc (docs/<project>-spec.md) instead of three
  • No docs/composants/catalogue-composants.md until 5+ components exist
  • No DDD discussion (auto-score < 5)
  • No CI files, no .husky (optional)
  • validate script: typecheck + lint + test

Skip: persona-simulator (no UX surface deep enough), full DDD scorecard interview.

Promotion signal to next archetype: spec grows past 30 FUNC IDs, OR live users land, OR second dev joins → Internal dashboard or Production SaaS depending on polish.

# Archetype B — Internal dashboard / tool

What it is: ops console, admin app, BI viewer, internal CRUD app for a known team.

Indicators: known small audience, no public marketing, may need auth + RBAC, schema is the spec.

Default scaffold:

  • React + Vite single app OR small apps/web + apps/api workspace if backend is non-trivial
  • Feature-first slices
  • All 3 source-of-truth docs (spec / data-model / catalogue)
  • Full palier 1 set
  • DDD scorecard run (likely lands 5-9 → strategic glossary only)
  • docs/security.md from day one (RBAC matrix lives here)
  • validate includes typecheck + lint + test + build

Skip: SEO/marketing concerns, public-facing performance budgets.

Promotion signal: the tool is replacing a paid SaaS internally, OR audience grows past one team → Production SaaS.

# Archetype C — Production SaaS

What it is: revenue-generating product, public marketing surface, paying customers, billing, multi-tenancy likely.

Indicators: real users, real money, real on-call rotation possible.

Default scaffold:

  • Next.js App Router single app OR apps/web + apps/api workspace
  • Framework-native + feature-first
  • All 3 source-of-truth docs
  • Full palier 1 set
  • DDD scorecard run (likely lands 5-9, sometimes ≥10 if billing/auth invariants are hard)
  • docs/architecture.md, docs/security.md, docs/agent-playbook.md, docs/decisions/ from day one
  • validate includes typecheck + lint + test + build + e2e
  • Promote to palier 4 (CI) early
  • seo-visibility skill (already global) wired in
  • Architecture checks (Knip, dep-cruiser) at palier 3+

Promotion signal to next archetype: monorepo with multiple deployables justified → Larger full-stack system.

# Archetype D — Larger full-stack system

What it is: multi-app, multi-package, multi-team. Web + admin + api + workers + docs site.

Indicators: ≥2 deployables, ≥2 teams, real shared packages (UI lib, schemas, domain).

Default scaffold:

  • pnpm workspace monorepo (apps/ + packages/)
  • Turborepo if simple package-task orchestration; Nx if affected/graph/AI-aware CI is core
  • Per-app: framework-native + feature-first
  • Shared: packages/ui, packages/schemas, packages/domain, packages/config-{eslint,typescript}
  • Full doc set + ADRs + agent-playbook
  • validate is graph-aware (nx affected -t lint test typecheck build or Turborepo equivalents)
  • Architecture checks (Knip, dep-cruiser, eslint-plugin-boundaries) at palier 1
  • DDD scorecard run per package; some packages land ≥10, others <5

No promotion — this is the terminal archetype for most projects. Further growth → split into multiple monorepos or service-extraction.

# Detection heuristics for analyze-project.mjs

Inputs:
- LOC
- Files / dirs at root
- package.json scripts
- presence of pnpm-workspace.yaml / turbo.json / nx.json
- presence of apps/ or packages/
- README hints (keywords: "internal", "demo", "prototype", "saas", "production")
- existing CI config

Heuristic:
  if (has pnpm-workspace.yaml AND has apps/ AND has packages/)        → Archetype D
  else if (has next.config.* OR has billing/ OR has stripe in deps)   → Archetype C
  else if (has auth/ AND no public marketing pages AND LOC < 5000)    → Archetype B
  else if (LOC < 500 AND no tests AND no CI)                          → Archetype A
  else                                                                 → ASK user

When ambiguous, prefer AskUserQuestion over silent assumption.

# How BOOTSTRAP uses archetype

In Step 4 of BOOTSTRAP (after stack convention pack):

  1. Run detection heuristic.
  2. Confirm with user (1 question, 4 options).
  3. Load archetype profile from this file.
  4. Merge with stack pack to produce final plan.
  5. Architect agent uses both as input.

Archetype is recorded in .claude/.meta-govern.json:

{
  "metaGovernVersion": "1.2.0",
  "archetype": "B",
  "palier": 1,
  "stack": "react-vite",
  "architecturePattern": "framework-native-feature-first",
  ...
}

This file is the single source of truth meta-govern reads on subsequent AUDIT / MIGRATE / ADVISE runs.

# Per-archetype palier ceiling

Some archetypes never need higher paliers:

Archetype Typical palier max
A — Prototype 1-2 (rarely 3)
B — Internal dashboard 3-4
C — Production SaaS 4-5
D — Larger system 5-6

If a prototype is at palier 5, something is wrong (over-built). AUDIT flags this.

# When archetype changes

Rare but real: a prototype graduates to internal dashboard, or an internal dashboard becomes a SaaS. Trigger:

Q. Has the project's audience or business model changed since BOOTSTRAP?
   NO  → archetype unchanged.
   YES → propose archetype migration in MIGRATE mode.

Archetype migration is a one-step plan: add the docs/skills/agents the new archetype needs. It does NOT re-scaffold from scratch.
