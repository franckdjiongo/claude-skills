Skill — Canonical Structure

Source: The-Complete-Guide-to-Building-Skills-for-Claude.md + observed patterns in user's existing skills.

# File structure

<skill-name>/                        # kebab-case, must match `name:` frontmatter
├── SKILL.md                         # exact filename (case-sensitive)
├── references/                      # lazy-loaded reference docs
│   ├── *.md
│   └── *.md
├── scripts/                         # bundled scripts (deterministic validation)
│   ├── *.mjs
│   └── *.py
├── templates/                       # file scaffolds
│   └── *.tpl
├── examples/                        # optional examples
└── assets/                          # static assets

Forbidden in skill folder:

  • README.md (Anthropic explicit ban — all docs go in SKILL.md or references/)
  • Folder names with spaces, underscores, or capitals
  • Files referenced as relative URLs to web (broken without internet)

# Frontmatter — required fields

---
name: skill-name                    # required, kebab-case, matches folder name
description: |                       # required, the targeting instruction
  [What it does, in 1 sentence].
  Use whenever the user [trigger 1], [trigger 2], [trigger 3], or any variant
  about [topic]. Distinct from [sibling skill 1] (does X) and [sibling skill 2]
  (does Y) — this skill [unique purpose].
---

# Frontmatter — optional fields

Field Use when
allowed-tools: Read, Write, Edit, ... Skill uses specific tools; restrict to those
model: opus|sonnet|haiku Skill has a preferred model (e.g., model: opus for design skills)
effort: low|medium|high|xhigh Skill has a preferred effort level (mostly omitted; let session default win)
disable-model-invocation: true Skill has side effects (deploys, schema mutations); only manually invoked
context: fork Skill body runs in a forked subagent context; main thread sees only summary
argument-hint: <usage> Skill is slash-invoked with arguments; describes the args
agent: <agent-name> Skill explicitly delegates to a subagent (e.g., agent: implementer)

# Frontmatter — forbidden

  • XML angle brackets (<, >) — security: prompt injection vector via system prompt
  • Names containing "claude" or "anthropic" — reserved
  • Names not in kebab-case
  • Multi-line name: (must be single line)

# Description shape (the high-leverage field)

Per Doc 4 research: aggressive language markers + precise targeting in description push activation from ~50% to 80-84%. Description structure:

[What it does — 1 sentence, action verb]
Use whenever the user [says X], [says Y], [says Z]
[explicit triggers like "/skill-name"], [paraphrased triggers]
or any variant about [topic / domain / artifact].
Distinct from [sibling 1] (which does A) and [sibling 2] (which does B) —
this skill [unique value proposition].

Good description (Brillance brainstorm skill):

Drive a structured design / brainstorming session for any feature, refactor, or
architecture decision in Brillance Décor Inc. Hard gate: NO implementation until
the design is approved section-by-section and a `## Source of truth delta` block
is written. Writes `docs/specs/YYYY-MM-DD-<topic>-design.md`. Use whenever the
user says: brainstorm, design, conception, architecture, "comment implémenter",
"comment ajouter", "plan d'attaque", "let's design", "how should we build X",
"réfléchissons à", "feature design", "spec a feature".

Bad description:

Helps with project design.

# SKILL.md body — recommended structure

# <skill-name>

[1-paragraph hook: what this skill does, who triggers it, what it produces.]

## When to use

[Bulleted list of exact trigger conditions. Same content as description but expanded.]

## Workflow

### Step 1: [name]
[Details]

### Step 2: [name]
[Details]

[...]

## Output contract

[What artifact(s) this skill produces, where they go, what shape they take.]

## Cross-references

- Reference X: when this is needed → load `references/x.md`
- Reference Y: when this is needed → load `references/y.md`

## Gotchas

[Highest-signal section. Per Doc 4: gotchas are the most-read content.
Concrete pitfalls observed in production, with fix.]

## Examples

[1-3 worked examples, each ending with the produced artifact.]

# Body length budget

  • Recommended: ≤2000 words
  • Hard cap: ≤5000 words (degraded triggering above this)
  • Override pattern: keep body lean, push detail to references/*.md (which load on demand)

# Three-level disclosure inside a skill

  1. Frontmatter (always loaded): ~50 tokens — the targeting instruction.
  2. Body (loaded when triggered): ~5K tokens — the workflow.
  3. References (loaded on demand): unbounded — the deep knowledge.

This is the analogue of the four-tier architecture inside a single skill.

# Cross-references convention

When the skill body needs to point at a reference:

For the full DDD scorecard, read `references/ddd-scorecard.md` before scoring.

Not:

@references/ddd-scorecard.md

The @ syntax embeds the file. Plain prose pointer makes the load conditional.

# Bundled scripts pattern

For critical validations, bundle a script. "Code is deterministic; language interpretation isn't" (Doc 5).

my-skill/
├── SKILL.md                    # references the script
└── scripts/
    └── validate-output.mjs     # exits 0 (clean) / 1 (findings) / 2 (error)

The skill body invokes the script via Bash:

After producing output, validate:

```bash
node scripts/validate-output.mjs <output-file>

Exit code 0 → done. Non-zero → fix findings, re-run.


## Hooks attached to skills

A skill can declare hooks specific to its scope (rare, mostly for subagents):

```yaml
---
name: my-implementer
hooks:
  PreToolUse:
    Edit|MultiEdit:
      - command: ".claude/hooks/skill-specific-edit-guard.mjs"
---

Used for: scoped enforcement (only when this skill / agent is active).

# Slash invocation

Skills with argument-hint: are slash-invocable:

---
name: my-skill
description: ...
argument-hint: <topic>
---

User types: /my-skill some topic → skill triggers with $ARGUMENTS = "some topic".

# Common patterns

Pattern Use when
Sequential workflow orchestration Multi-step pipelines (e.g., brainstorm → write-plan → execute-plan)
Multi-MCP coordination Combining 2+ MCP servers (e.g., Notion + Linear)
Iterative refinement Quality criteria + validation loop (e.g., quality-gate)
Context-aware tool selection Picks tool based on context (e.g., debug skill picks Bash vs JS)
Domain-specific intelligence Heavy domain knowledge in skill body (e.g., domain-driven-design)

# Testing a skill

After authoring or modifying a skill:

  1. Triggering test: Does Claude invoke the skill on representative prompts?

    • Try 5+ obvious prompts → should trigger 5/5
    • Try 5+ paraphrased → should trigger 4/5
    • Try 5+ unrelated → should NOT trigger

  2. Functional test: Does the skill produce valid output?

    • Run the workflow end-to-end
    • Check output artifact shape
    • Check edge cases (empty input, malformed input, conflicting input)

  3. Performance comparison: Does the skill help vs. not having it?

    • With-skill vs without-skill on the same prompt
    • Tool call count, token usage, error rate

skill-creator plugin has eval tooling for this.

# Iteration triggers

Signal Action
Under-triggering (<70% on relevant queries) Add keywords to description; add trigger phrases
Over-triggering (firing on unrelated prompts) Add negative triggers ("Do not use when...")
Execution issues (skill triggers but fails) Add error handling; bundle scripts; tighten output contract
User asks "what next" mid-skill Workflow ambiguous; clarify steps + transitions

# When to retire a skill

  • 0 invocations in 90 days
  • Subsumed by another skill (consolidate)
  • Domain disappeared from project (e.g., migrated off Convex)
  • Contains stale model assumptions (e.g., still references a retired model — Opus 4.6/4.7, Sonnet 4.6, or Fable 5/Mythos 5, retired from this workflow on 2026-07-07)

Retirement = delete folder + update governance baseline.

# Anti-patterns recap (with this reference's authority)

❌ README.md inside skill folder ❌ Variations of SKILL.md filename (skill.md, SKILL.MD) ❌ Folder name not kebab-case ❌ XML angle brackets in frontmatter ❌ "claude" or "anthropic" in skill name ❌ Vague description ("helps with X") ❌ Body >5000 words ❌ disable-model-invocation: false on side-effect skills ❌ @filename imports in skill body ❌ Defensive scaffolding ("MUST", "ALWAYS") in body — only allowed in description for activation
