DDD Applicability Scorecard

Source: Domain-Driven Design - A Production Reference.md §7.1, adapted.

# When DDD pays back

DDD's strategic half (bounded contexts, ubiquitous language, context maps) almost always pays back at system-of-systems scale. DDD's tactical half (entities, VOs, aggregates, repositories) is optional — it's a heavy investment that only pays back when the domain has rich invariants.

The 8-item scorecard quantifies whether this project deserves full DDD, strategic-only, or none.

# The 8 items

Score 0 (no), 1 (partial / unclear), or 2 (yes) for each.

# Question Score
1 Is the product a key competitive differentiator for the business? 0/1/2
2 Are the business rules contested between stakeholders (or change frequently)? 0/1/2
3 Will this product live longer than 2 years? 0/1/2
4 Will multiple teams work on it? 0/1/2
5 Are domain experts reachable for ongoing collaboration? 0/1/2
6 Does the domain have non-trivial invariants (state machines, transactions, refunds, multi-step approvals)? 0/1/2
7 Does the system have multiple integrations (3+ external systems)? 0/1/2
8 Is the system multi-tenant with isolation requirements per tenant? 0/1/2

Max score: 16.

# Interpretation

≥ 10  → FULL DDD
        Bounded context canvas, glossary, context map, aggregates per AR,
        repositories per AR, anti-pattern hooks, event-driven where useful,
        Strangler Fig for legacy.

5 - 9 → STRATEGIC + LIGHT TACTICAL
        Glossary + context map (even sketch), package by feature, value objects
        for primitives, but skip aggregate-per-transaction unless rules demand.
        Most "well-designed CRUD" projects land here.

< 5   → TRANSACTION SCRIPT / ACTIVE RECORD
        Don't force DDD. Use clean ordinary code. Apply KISS aggressively.
        Most simple SPAs, marketing sites, internal tools land here.

# Power Platform / Dataverse mapping

For Power Apps code apps + Dataverse:

  • Dataverse environments often are bounded contexts. One environment = one BC.
  • C# plugins are aggregate transactional boundaries (sandboxed transaction = aggregate transaction).
  • Power Automate flows are orchestration (process managers / sagas), NOT the domain.
  • Plugins should be thin: delegate to pure domain classes. Plugin = adapter.

If the user is on Power Platform AND scores ≥10:

  • Bounded contexts map 1:1 to Dataverse environments
  • Plugins implement aggregate behavior; flows orchestrate
  • Mapper-as-ACL: never let Dataverse types leak into the domain

# When subdomains migrate

A subdomain's classification is NOT locked. Khononov's "Black Swan core": a generic subdomain becomes core when you start innovating on it (Tune's example: pricing, originally generic, became their differentiator).

  • Generic (low differentiation, low complexity) → buy / use a library
  • Supporting (low differentiation, high complexity) → build simply, don't over-engineer
  • Core (high differentiation, high complexity) → invest heavily, own the ubiquitous language
  • "Hidden core" warning (high differentiation, low complexity) → commoditize quickly OR automate; otherwise you'll lose the differentiation

Re-score every 6-12 months.

# Anti-pattern: DDD-Lite

Doc 2 §V warns about DDD-Lite: applying tactical patterns (entities, VOs, aggregates, repositories) without doing the strategic work (bounded contexts, ubiquitous language). This is worse than not doing DDD at all — you pay the ceremony tax without getting the boundary clarity.

meta-govern's scorecard prevents this: tactical scaffolding only happens at score ≥10, where strategic artifacts are also produced. Score 5-9 produces only strategic. Score <5 produces neither.

# Honest disclosure

For most projects the user works on (small client SaaS, marketing sites, code apps), the score will be <5 or 5-9. That's fine. KISS first; DDD only when the score earns it.

The exception: Temps Chantier (Groupe Gilbert) is a complex Dataverse-driven workflow product → likely scores ≥10 and uses Mapper-as-ACL pattern explicitly.
