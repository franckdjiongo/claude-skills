DDD — Strategic Design (Quick Reference)

This reference is a quick map. For full guidance, invoke the existing master skill domain-driven-design (already global at ~/.claude/skills/domain-driven-design/).

# When to apply

  • Project DDD score ≥ 5 (per ddd-scorecard.html)
  • Multiple bounded contexts emerging
  • Team needs shared ubiquitous language

# The 4 strategic artifacts

# 1. Glossary (ubiquitous language)

Located at docs/architecture/glossary.md. Each BC has its own glossary section.

# Glossary — <project>

## Bounded Context: Billing

- **Invoice**: A request for payment for goods or services rendered. Has line items, due date, status.
- **Charge**: An attempt to capture money on a payment method. Belongs to one Invoice.
- **Refund**: A reversal of a Charge. May be partial.

## Bounded Context: Inventory

- **SKU**: Unique product identifier. Internal only.
- **Variant**: A SKU with specific attributes (size, color). Customer-facing.

Glossaries live next to code (per feature-package org). Update during brainstorm.

# 2. Bounded Context Canvas (per BC)

Located at docs/architecture/bounded-context-canvas-<bc>.md.

Sections:

  • Name + 1-line description
  • Strategic classification (Core / Supporting / Generic + rationale)
  • Domain roles (input / output)
  • Ubiquitous language (link to glossary)
  • Business decisions (which decisions live here?)
  • Inbound communication (commands accepted)
  • Outbound communication (events emitted)
  • Persistence (what stores, what schema)
  • Team ownership

# 3. Context Map

Located at docs/architecture/context-map.md.

Shows BCs as nodes, integration patterns as edges:

  • Partnership (mutual evolution, shared roadmap)
  • Shared Kernel (shared models, dangerous if BCs evolve apart)
  • Customer-Supplier (consumer drives provider's roadmap)
  • Conformist (consumer accepts provider's model)
  • Anti-Corruption Layer (translation layer at boundary)
  • Open Host Service (provider exposes versioned public contract)
  • Published Language (shared vocabulary, e.g., schema.org)
  • Separate Ways (no integration)
  • Big Ball of Mud (anti-pattern)

# 4. Core Domain Chart

Khononov's 2021 framing: business differentiation × model complexity, with subdomains plotted on the 2x2.

  • Core (high diff, high complexity) → invest, own
  • Supporting (low diff, high complexity) → build simply
  • Generic (low diff, low complexity) → buy
  • Hidden core warning (high diff, low complexity) → commoditize quickly

Re-score every 6-12 months.

# Power Platform mapping

  • Dataverse environment = Bounded Context (often 1:1)
  • C# plugin = Aggregate transactional boundary
  • Power Automate flow = Process Manager (orchestration, NOT domain)
  • Custom connector = ACL (anti-corruption layer)

# Anti-Corruption Layer (mapper-as-ACL)

For Dataverse + DDD:

Domain (pure TS, zero Dataverse types)
   ↑
   Mapper (translates Dataverse rows → Domain entities)
   ↑
Repository (interface in domain, impl in infrastructure)
   ↑
Dataverse SDK (generated services)

NEVER let Dataverse types (@odata.bind, _value, FormattedValue) into domain. Mapper translates.

# EventStorming (discovery)

Three levels:

  1. Big-picture: domain events on a wall, sorted chronologically
  2. Process-level: add commands, actors, policies, read models
  3. Design-level: add aggregates, invariants, scenarios

Output:

  • Bounded contexts emerge from event clusters
  • Aggregates emerge from invariant clusters
  • Read models emerge from query needs

# When meta-govern installs DDD strategic artifacts

In BOOTSTRAP, if DDD score ≥ 5:

  • docs/architecture/glossary.md (skeleton, user fills in)
  • docs/architecture/context-map.md (skeleton, single BC by default)

If DDD score ≥ 10:

  • All of the above
  • docs/architecture/bounded-context-canvas-<bc>.md (per BC)
  • docs/architecture/core-domain-chart.md
  • .claude/rules/ddd-strategic.html (path-scoped to docs/architecture/**)
