Tooling — Architecture Checks

Source: synthesis of LLM-friendly project architecture for AI coding agents in 2026.md plus the user's existing quality-checks/ script suite.

Three machine-checkable architecture tools complement the existing 12-check quality-checks/ script. They are opt-in, recommended at specific paliers.

# The three tools

# Knip — unused files / exports / dependencies

What: static analysis that walks package.json, source files, and config to flag:

  • unused exports
  • unused files
  • unused dependencies
  • unused devDependencies

When to add: palier 3+ (multi-dev) or any time the codebase has >50 source files.

Why agents care: dead code shows up in agent searches and wastes context. Pruning improves discoverability.

Install:

bun add -D knip

Wire into validate:

{
  "scripts": {
    "lint:dead": "knip",
    "validate": "... && bun run lint:dead && ..."
  }
}

Config (knip.json):

{
  "$schema": "https://unpkg.com/knip@5/schema.json",
  "entry": ["src/main.tsx", "src/app/**/*.{ts,tsx}"],
  "project": ["src/**/*.{ts,tsx}"],
  "ignore": ["src/test/**"]
}

Severity policy (in validate): start as warning-only; promote to blocker once the team is at zero findings.

# dependency-cruiser — circular deps, missing deps, orphans

What: rule-based dependency analyzer:

  • detects circular import cycles
  • detects missing/extraneous dependencies
  • detects orphan files (no incoming references)
  • enforces custom forbidden-edge rules

When to add: palier 2+ if the project has >100 files, OR any time a circular import is observed.

Why agents care: circular deps cause non-deterministic load order; agents make wrong assumptions. Orphans waste search time.

Install:

bun add -D dependency-cruiser

Wire into validate:

{
  "scripts": {
    "lint:deps": "depcruise --config .dependency-cruiser.cjs src",
    "validate": "... && bun run lint:deps && ..."
  }
}

Config (.dependency-cruiser.cjs): start with npx depcruise --init and pick the recommended preset. Add custom rules per project (e.g., features/* must not import from features/* to enforce slice independence).

# eslint-plugin-boundaries — architectural import enforcement

What: ESLint plugin that enforces import direction between named "elements" of the codebase. Configurable: layers, modules, slices.

When to add: palier 3+ multi-dev, OR archetype D (monorepo / FSD-light).

Why agents care: without enforcement, slices leak into each other and the architecture decays into spaghetti. Enforcement turns architectural intent into machine-checkable feedback.

Install:

bun add -D eslint-plugin-boundaries

Config (in eslint.config.js):

import boundaries from 'eslint-plugin-boundaries';

export default [
  {
    plugins: { boundaries },
    settings: {
      'boundaries/elements': [
        { type: 'app', pattern: 'src/app/**' },
        { type: 'feature', pattern: 'src/features/*' },
        { type: 'shared', pattern: 'src/shared/**' },
        { type: 'route', pattern: 'src/routes/**' }
      ]
    },
    rules: {
      'boundaries/element-types': ['error', {
        default: 'disallow',
        rules: [
          { from: 'app', allow: ['feature', 'shared', 'route'] },
          { from: 'route', allow: ['feature', 'shared'] },
          { from: 'feature', allow: ['shared'] },
          { from: 'shared', allow: ['shared'] }
        ]
      }]
    }
  }
];

This config encodes: routes can use features, features cannot import other features, everything can use shared. The lint error explains exactly why an import is rejected — agents fix it deterministically.

# Decision matrix

Project state Knip dep-cruiser eslint-plugin-boundaries
Archetype A, palier 1 skip skip skip
Archetype B, palier 1-2 skip optional skip
Archetype B, palier 3+ recommend recommend optional
Archetype C, palier 1-2 recommend recommend optional
Archetype C, palier 3+ required required recommend
Archetype D (any palier) required required required
Any archetype with observed circular imports n/a required n/a
Any archetype with features/* cross-imports leaking n/a n/a required

# Integration with existing quality-checks

The user's existing quality-checks/ script does:

  • hardcoded colors (hex / rgba)
  • i18n bypass
  • file size > 300 lines
  • any types
  • console.log
  • secret patterns
  • direct fetch() in components
  • snapshot tests
  • container.querySelector
  • useEffect+setState heuristic
  • TODO markers
  • project-specific checks

These three tools are architectural (file-graph level), not per-file (line level). They're complementary. Quality-checks runs first (fast feedback); architecture checks run last in the validate chain (slower, broader).

Recommended validate order:

1. typecheck      (fastest, catches the most)
2. lint           (eslint, including boundaries plugin)
3. test           (unit/integration)
4. quality:check  (per-file rules, 12 checks)
5. lint:deps      (dependency-cruiser, only when added)
6. lint:dead      (knip, only when added)
7. build          (last — slowest, requires the rest passing)

# When NOT to add these

  • Archetype A prototypes — adds friction with no benefit.
  • A codebase under heavy refactor — false positives explode; defer until refactor lands.
  • A team that won't fix findings — running and ignoring is worse than not running. Only add if validate is allowed to fail on findings.

# Migration playbook (when adding mid-project)

  1. Install + add config in a feature branch.
  2. Run once; capture findings to docs/<date>-<tool>-baseline.md.
  3. Fix critical findings only (circulars, missing deps, blatant unused).
  4. Add to validate with --fail-level=error for the new findings only (most tools support a baseline).
  5. Triage the rest in docs/backlog-deferred.md.
  6. Tighten over time; never block CI on baseline-day findings.

This avoids the "add the tool, get 200 findings, abandon" failure mode.
