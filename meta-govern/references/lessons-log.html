2026-06-22 — Temps Chantier — Audit reverse-engineering du pipeline design→plan→implémentation → meta-govern v1.4.0 #

Project: Temps Chantier (audit du pipeline de skills) → généralisé dans meta-govern
Severity: HIGH
Type: WORKFLOW
Recurrence: 1re (audit-driven ; 3 workflows convergents — 7 skills notés, 47 designs + 57 plans scorés, 1306 transcriptions minées + 18 lues en profondeur)

# What happened

L'audit conclut que le pipeline livre rarement du faux (une seule sortie défectueuse a atteint l'utilisateur sur 18 sessions friction-denses, immédiatement revertée) mais paie la qualité en reprises (remediation dans ~89 % des lots). Le maillon faible est en amont : l'étage design (noté B) et la précision d'entrée des tâches (plan), pas le moteur d'exécution. Le skill TDD est noté C parce que les garde-fous (relire les critères d'acceptation, prouver-par-retrait, preflight typecheck, arrêt sur entrée déficiente) vivent dans le corps de l'agent tc-implementer mais pas dans le skill. Une seule sortie fausse ayant atteint l'utilisateur (UI sous-traitance) venait d'un « visuel non vérifié » soft-disposé 3 fois.

# Root cause

Les critères d'acceptation n'étaient jamais exigés comme conditions observables par comportement ; le flou du design se propageait à l'aval. Les cas limites vivaient en prose hors des cases à cocher ; aucune traçabilité design→tâches (seulement tâche→spec) ; le gate d'entrée d'execute était structurel (le bloc Stratégie existe-t-il ?) jamais de contenu ; aucun gate dur pour la QA visuelle (jsdom est aveugle au rendu) ni pour la frontière réelle (1584 tests verts sur mocks pendant que l'app cassait sur le vrai Dataverse).

# Action taken

# Lesson generalized

La rigueur appartient à l'amont : des critères d'acceptation OBSERVABLES par comportement dans le design, rendus en cases à cocher exécutables dans le plan, dont la couverture design→tâches est prouvée, et contrôlés par un gate de CONTENU (pas seulement de structure) à l'exécution — c'est le plus court chemin de « rarement faux mais souvent repris » à « correct du premier coup ». Corollaire : un test vert sur mock idéalisé / jsdom ne prouve pas la frontière réelle ni le rendu — la vérification d'intégration et la QA visuelle sont des gates de première classe, non-reportables. Quand un garde-fou ne vit que dans le corps d'un agent, il faut le porter dans le skill pour qu'il survive au changement de l'agent.

2026-06-22 — meta-govern self — Bootstrapped skill bodies pointed to references/*.md the BOOTSTRAP never installed → v1.4.1 #

Project: meta-govern itself (v1.4.0 → v1.4.1 patch)
Severity: MEDIUM
Type: TOOLING
Recurrence: 1re (le suivi explicitement différé dans lesson-2026-06-22-1, désormais traité)

# What happened

Quatre templates de skills (brainstorm, write-plan, quality-gate, govern-claude) référençaient des fichiers frères references/*.md (section-templates.md, delta-format.md, self-review-checks.md, checks-catalog.md, evolution-roadmap.md, authoring-best-practices.md, session-lessons.md) que bootstrap-project.mjs n'installe jamais — son plan par défaut n'installe qu'UNE référence de skill, govern-claude/references/baseline.md (ligne 346). Chaque projet bootstrappé portait donc des pointeurs morts dans des corps de skills par ailleurs auto-suffisants.

# Root cause

Les corps de skills ont été rédigés selon une convention « les détails vivent dans un fichier frère references/ » qui n'a jamais été câblée dans le plan de bootstrap. Aucune source fondée n'existait pour authoring ces 7 fichiers (les skills mûrs de Temps Chantier utilisent d'AUTRES noms de fichiers) — les créer serait de l'invention. Aucune garde déterministe ne reliait « pointeur references/*.md dans un template » à « fichier installé par le bootstrap ».

# Action taken

# Lesson generalized

Un corps de skill ne doit pointer que vers des fichiers que le BOOTSTRAP installe réellement : soit inliner le contenu porteur, soit rediriger vers un artefact installé (règle .claude/rules/*.md, script .claude/scripts/**) ou vers le canon meta-govern globalement présent (chemin absolu ~/.claude/skills/meta-govern/references/*.html) — jamais vers un fichier frère references/*.md fantôme. Quand on ne peut pas authoring un fichier sans inventer, on redirige vers le grounded existant plutôt que de halluciner. Et tout invariant pointeur↔installation se promeut en garde self-audit déterministe (même schéma que la promotion règle→hook).

2026-06-26 — EOSA CAMPUS AUDIT — Refactor mono-app → monorepo : les path-globs root-relatifs des règles meurent en silence, et audit-project.mjs ne le détecte pas #

Project: EOSA CAMPUS (1 app SvelteKit/npm → monorepo bun, apps/eosa plateforme Convex + apps/boutique vitrine statique)
Severity: HIGH
Type: DRIFT
Recurrence: 1re (nouveau pattern : passage mono-app → monorepo / 2e contexte borné)

# What happened

Le code est passé sous apps/*/src (et Convex sous apps/eosa/convex), mais toute la couche de gouvernance déclarative décrivait encore le monde mono-app. Les 8 règles path-scoped pointaient src/** / convex/** (root-relatifs) : elles ne matchent plus rien sous apps/* — clean-code, file-size-budget, ui-components, data-layer se chargeaient sur ZÉRO fichier source réel (mortes, sans aucune erreur). CLAUDE.md (stack/commandes npm, convex/schema.ts racine, palier 1), docs-map.json (1 seule racine docs), baseline et .meta-govern.json (palier 1, loc 0, multiRuntime false) étaient tous périmés. La 2e app introduisait une 2e source de vérité (apps/boutique/docs/boutique-spec.html) invisible à la gouvernance, et le hook block-docs-markdown ne gardait que la racine docs/.

# Root cause

audit-project.mjs n'est pas monorepo-aware : il n'a remonté que 4 findings mineurs et a entièrement manqué la dérive #1 (globs morts). Les scripts de gate (quality-checks, size-guard) avaient déjà été patchés pour le monorepo (ils classent apps/<name>/… comme racine d'app), mais la couche déclarative n'a aucune garde reliant « glob d'une règle » ↔ « au moins un fichier réel matché ». Un glob qui ne matche rien est silencieux : pas d'erreur, juste une règle qui ne se charge jamais.

# Action taken

  • Globs des règles re-scopés apps/*/src/** et apps/eosa/convex/** ; spec-protocol couvre apps/boutique/docs/boutique-spec.html.
  • CLAUDE.md réécrit (monorepo, 2 contextes bornés, commandes bun, Convex scopé à apps/eosa, palier 2) ; docs-map.json v2 (2e contexte enregistré) ; block-docs-markdown élargi à apps/*/docs/ ; baseline + .meta-govern.json rafraîchis.
  • Miroirs .codex/ + .agents/ resynchronisés byte-identical ; npm run → bun run dans les skills/agents gouvernés.
  • QA : bun run validate vert (check + 12 tests + build ×2 + quality:check clean) ; coherence-validator PASS (findings LOW). Aucun fichier source d'app touché.

# Lesson generalized

Un refactor mono-app → monorepo est une dérive de gouvernance silencieuse de première classe : les path-globs root-relatifs (src/**, convex/**) cessent de matcher dès que le code descend sous apps/*/ — la règle existe mais ne se charge jamais, sans aucune erreur. À promouvoir dans audit-project.mjs : (1) une garde déterministe « glob-de-règle ↔ existence d'au moins 1 fichier matché » (HIGH si une règle ne matche aucun fichier réel), et (2) une détection monorepo (présence de workspaces / apps/*) qui signale tout glob root-relatif non préfixé apps/*. Corollaire : une 2e app = un 2e contexte borné → 2e source de vérité, 2e racine docs (le toolkit docs-html mono-racine doit devenir paramétrable), et toute règle data/backend (ex. Convex-only) doit être scopée à l'app concernée, pas énoncée globalement.

2026-06-26 — EOSA CAMPUS — Toolkit docs-html mono-racine + piège du */ dans les commentaires JSDoc des hooks #

Project: EOSA CAMPUS (suites de l'audit monorepo : 2 tâches de suivi)
Severity: MEDIUM
Type: TOOLING
Recurrence: 2e (corollaires de lesson-2026-06-26-1 ; le piège */ a mordu DEUX fois dans la même session)

# What happened

Deux dérives induites par le monorepo, invisibles tant qu'on reste mono-app. (1) Toolkit docs-html mono-racine : make-index.mjs + lib/docs-config.mjs codaient DOCS_ROOT="docs" en dur, donc apps/boutique/docs/ n'apparaissait dans AUCUN hub généré ; et le hook docs-index-refresh mirroité dans .codex/ pointait hookDir/../scripts/docs-html = .codex/scripts/docs-html (inexistant — le toolkit ne vit que sous .claude/), donc le rafraîchissement Codex était un no-op silencieux. (2) Piège */ : écrire le glob apps/*/docs/ DANS un commentaire bloc /* … */ referme le commentaire au */ — le hook ne parse plus (« Unexpected identifier »). Ce footgun a cassé block-docs-markdown puis docs-index-refresh dans la même session.

# Action taken

  • DOCS_ROOT/HUB_TITLE rendus surchargeables par env (défaut inchangé) → tout le toolkit devient multi-racine sans toucher les autres modules ; wrapper index-extra.mjs (sync assets + make-index enfant) + scripts docs:index:boutique/docs:index:all ; hub Boutique généré.
  • docs-index-refresh généralisé aux DEUX racines et résout le toolkit via repoRoot/.claude/scripts/docs-html → fichier identique ET fonctionnel depuis .claude/ comme .codex/ (corrige le no-op Codex). Garde la parité de filtres (pas de régénération à chaque Stop).
  • Glob réécrit apps/<app>/docs/ dans les commentaires ; node --check systématique après chaque édition de hook.

# Lesson generalized

(1) Tout outillage « racine unique » (docs-html, guards, index) doit devenir paramétrable dès qu'un 2e dossier (app, package) apparaît — préférer une surcharge par env sur l'UNIQUE module de config (threading automatique) à un refactor de chaque consommateur. (2) Un hook mirroité dans .codex/ qui appelle un outil ne vivant que sous .claude/ doit résoudre ce chemin depuis repoRoot/.claude/…, jamais hookDir/../… — sinon no-op silencieux côté Codex. (3) Footgun à promouvoir en garde scaffolder/hook-generator : ne JAMAIS écrire un chemin contenant */ (ex. apps/*/docs/) dans un commentaire bloc /* */ — utiliser apps/<app>/docs/ ou un commentaire ligne // ; et lancer node --check sur chaque .mjs généré/édité avant de conclure.

2026-06-26 — automintech — Transformer les leçons d'une rétrospective en gouvernance sur un projet palier 0, SANS bootstrap complet #

Project: automintech (Vite + React 19 + TS + Convex, bilingue FR/EN, palier 0, jamais bootstrappé — .claude/ ne contenait que des skills de capacité, aucun tier règles/hooks/agents)

Pièges écartés : (1) dérouler le BOOTSTRAP complet que l'utilisateur n'a pas demandé ; (2) déposer des .claude/rules/*.md en supposant qu'un loader manque. 2026-06-26 — automintech — BOOTSTRAP 0→1 + MIGRATE html-docs sur un projet déjà mature : trois bugs d'outillage déterministe à promouvoir #

Project: automintech (Vite + React 19 + Convex, backend mûr, AGENTS.md déjà présent, 77 docs .md) — BOOTSTRAP palier 0→1 puis MIGRATE --target=html-docs enchaînés en une session
Severity: MEDIUM
Type: TOOLING
Recurrence: 1re (bootstrap d'un projet déjà mature ; 3 bugs distincts dans le même run)

# What happened

Trois défauts déterministes, chacun silencieux. (1) Inflation de palier au re-detect : bootstrap-project.mjs (ligne ~121) et migrate-project.mjs appellent detectProject() APRÈS avoir écrit les artefacts, puis persistent detection.palier. Un bootstrap 0→1 a donc écrit palier: 5 (le tier de gouvernance fraîchement posé + AGENTS.md + docs riches déclenchent l'heuristique de maturité), incohérent avec le CLAUDE.md rendu (« Current palier: 1 »). La migration a ré-écrasé le correctif manuel à 5. Re-fix manuel à 1 requis DEUX fois. (2) Glob comma-string → un seul item YAML : l'architect a posé SOURCE_GLOB="{components,…}/**/*.{ts,tsx},*.{ts,tsx}" (chaîne jointe par virgule) ; les templates de règles rendent paths:\n - {{SOURCE_GLOB}} → UN item de liste contenant une virgule, donc l'arme racine *.{ts,tsx} (App.tsx, types.ts) est silencieusement ignorée — et le brace de répertoire {a,b,c}/ n'est pas garanti matché par le path-matcher. (3) Hooks docs câblés en chemin relatif nu : block-docs-markdown + docs-index-refresh dans settings.json = node .claude/hooks/…, alors que les 5 hooks cœur = node "${CLAUDE_PROJECT_DIR}/.claude/hooks/…" → no-op silencieux si le CWD ≠ racine projet.

# Action taken

  • Bootstrap lancé avec --overwrite APRÈS un commit-checkpoint des règles/CLAUDE.md faits main : le CLAUDE.md lean templaté atterrit, git préserve la prose riche (relocalisée en docs/architecture.html par le source-of-truth-scaffolder). La règle ui-components écrasée a été re-mergée à la main (section « fonds pleine largeur »).
  • MIGRATE html-docs sûr sur projet déjà bootstrappé : le toolkit se re-rend en overwrite:false (couleurs de marque correctes préservées) ; préflight npm i --no-save markdown-it… requis ; suppression des .md restée manuelle (filet de sécurité) ; gate de fidélité 77/77 PASS avant git rm.
  • 3 findings du workflow-validator corrigés : palier 1, hooks docs en ${CLAUDE_PROJECT_DIR}, globs paths: éclatés en items YAML explicites (par répertoire + racine quotée).

# Lesson generalized

À promouvoir dans l'outillage : (1) un BOOTSTRAP 0→N doit persister le palier CIBLE explicitement (1 pour 0→1), jamais un detectProject() post-écriture — sinon l'heuristique compte les artefacts qu'on vient de poser et gonfle le palier ; idem migrate ne doit pas ré-écraser le palier déclaré. Corollaire AUDIT : audit-project.mjs devrait réconcilier « palier détecté » vs « palier déclaré (state file) » plutôt que recalculer aveuglément. # 2026-08-02 — meta-govern self (port personal-budget-app) — Tester un garde ne suffit pas : il faut tester ses CONTOURNEMENTS et ses INTERFACES → v1.16.2

Une revue adversariale multi-agents avait établi, dans personal-budget-app, que deux hooks livrés par les templates de ce dépôt ne faisaient pas ce qu'ils prétendaient — et les DEUX avaient des tests co-localisés VERTS. (1) templates/hooks/lib/bash-write-detect.mjs.tpl : REDIRECT_RE scannait le texte brut sans conscience d'un guillemet englobant ; bash -c 'cat > docs/x.md' produisait la cible docs/x.md' (apostrophe traînante) — les comparaisons exactes en aval échouaient et l'écriture était AUTORISÉE, un contournement trivial des deux seules règles inconditionnelles du garde. Aucun test existant n'enveloppait jamais une commande dans bash -c : la table de vecteurs ne testait que des formes canoniques (cat > x, tee, sed -i…), jamais leur contournement le plus évident. (2) templates/hooks/agent-dispatch-preflight.mjs.tpl écrivait une chaîne ISO nue dans la sentinelle .batch-in-flight ; un lecteur qui la reparserait en JSON lèverait et traiterait la sentinelle comme absente. Le test existant vérifiait seulement que le hook producteur s'exécutait sans erreur (exit 0, fichier créé) — jamais que le fichier produit survivait à une relecture par son VRAI consommateur de l'autre côté de l'interface. (3) En portant le test manquant de plan-closeout-guard.mjs.tpl (aucun template de test n'existait pour ce garde), le rendu du template CANON contre ce nouveau test a échoué : PENDING-MANUAL y a une portée PAR SECTION (body.includes('PENDING-MANUAL')) depuis sa création en v1.8.0, alors que le contrat documenté — et l'implémentation déjà corrigée dans personal-budget-app, servant de référence à ce port — exige une portée PAR CASE (le marqueur dans le MÊME <li> que la case qu'il exempte). Un troisième défaut de la même classe, jamais signalé, découvert seulement parce que le NOUVEAU test a été exécuté contre le VRAI template avant d'être livré.

# Root cause

Trois variantes d'un même angle mort. (1) Une table de vecteurs testée exhaustivement sur ses ENTRÉES CANONIQUES ne prouve rien sur ses ENVELOPPES — un attaquant (ou un usage légitime) qui enrobe la commande dans bash -c '…'/sh -c "…" change la syntaxe visible sans changer l'intention, et un détecteur texte-brut voit une chaîne différente de celle qu'il a apprise à reconnaître. (2) Un test qui vérifie qu'un PRODUCTEUR ne plante pas ne vérifie pas que son produit est UTILISABLE par le CONSOMMATEUR réel de l'autre côté du contrat — existsSync(sentinelPath) était vrai avant ET après le correctif, ce qui rendait le test aveugle au défaut qu'il était censé attraper. (3) Un template de garde peut porter une docstring qui DÉCRIT le bon contrat (« portée par case ») sans que le CODE l'implémente — rien ne le contredit tant qu'aucun test n'exerce la divergence entre les deux, et une revue qui lit la prose sans exécuter le code contre un cas adversarial la prend pour argent comptant.

# Action taken

# Lesson generalized

Un garde peut être testé et néanmoins inopérant si ses tests n'exercent que les formes CANONIQUES de ce qu'il doit attraper. Deux classes de cas manquent systématiquement à une suite qui se contente de la forme directe : le CONTOURNEMENT (la même intention réécrite sous une syntaxe différente — une enveloppe shell, un alias, un chemin absolu au lieu de relatif) et l'INTERFACE (le produit d'un hook n'est prouvé correct que s'il est relu avec succès par son VRAI consommateur, jamais par une assertion qui s'arrête à « le fichier existe » ou « le process n'a pas planté »). Ajouter un test à un garde qui n'en avait aucun n'est pas un exercice neutre : exécuter ce test contre le code EXISTANT avant de le livrer est le seul moyen de savoir si le contrat documenté et le contrat implémenté ont divergé — la docstring d'un garde n'est une preuve de rien tant qu'aucun test ne l'a mise en défaut.

Le risque n'est pas cosmétique : c'est un outil de gouvernance qui, faute de mémoire, propose de détruire ce qu'il est censé protéger.

Corollaire méthodologique. Le sous-agent governance-auditor a correctement démonté les faux positifs qu'il a prouvés par exécution (il a lancé les deux hooks et constaté leurs codes de sortie) — et s'est trompé sur le seul finding qu'il a bâti sur un comptage partiel : un ls docs/*.html limité à la racine lui a fait conclure « 21 Markdown contre 3 HTML, doctrine mixte incohérente », là où un find récursif donne 56 HTML contre 21 Markdown, dont 48 plans sous docs/plans/ — une répartition qui suivait exactement la doctrine. Il recommandait un arbitrage de fond ; les vraies violations étaient 1 à 2 fichiers. Re-compter soi-même coûte une commande ; l'erreur évitée était une migration de 21 fichiers.

Action prise (v1.17.0). L'audit devient déclaration-aware : palier déclaré prime sur l'inférence (qui rendait 0 dès que < 3 skills coeur étaient présents, écrasant un projet mature) ; inventoryPolicy:'lean-by-design' replie 23 findings en une ligne INFO récapitulative ; docsDoctrine:'markdown-agent-facing' devient un carve-out nommé, promu dans la doctrine globale des deux runtimes — le test est le LECTEUR du document, pas son emplacement ; sourcesOfTruth déclarées remplacent la recherche par chemins, avec vérification sur disque (une déclaration périmée est HIGH — déclarer n'est pas être dispensé). Plus deux heuristiques corrigées : le durcissement PATH est accepté au site d'invocation autant que dans le script, et un garde consultatif (ni exit 2, ni permissionDecision:'deny') ne se voit plus réclamer un cas « deny/block » qu'il ne peut structurellement pas produire — sa paire positif/négatif est « émet l'avis » vs « reste silencieux ».

Vérification. workstation 43 → 5 findings (1 HIGH réelle, 4 INFO déclaratives), palier lu à 4 ; self-audit 0 finding ; non-régression confirmée sur deux projets gouvernés ne portant pas les nouvelles clés (power-platform-ai-toolkit 22 findings palier 5, second-brain 13 findings palier 5). Toute suppression est conditionnée à une déclaration explicite.

# Lesson generalized

Une décision de gouvernance doit vivre dans un format que l'outillage sait LIRE, pas seulement dans une prose que l'humain sait relire. Une exemption qui n'existe qu'en prose sera re-litigée à chaque audit, et finira par être « corrigée » par un outil qui n'avait aucun moyen de savoir qu'elle était intentionnelle — un audit sans mémoire des arbitrages passés ne mesure pas la dérive, il la fabrique. Corollaire pour les sous-agents : leurs affirmations prouvées par EXÉCUTION tiennent ; celles dérivées d'un listing non exhaustif cassent — re-compter soi-même avant d'agir sur un finding quantitatif coûte une commande, et c'est le meilleur rapport qualité-prix de tout le mode AUDIT.
