Model & Effort Defaults — Selection Guide

Sources: Claude 5 Workflow Playbook (2026-07-01, QA-verified distillation of Anthropic's prompting guides + the Sonnet 5 System Card; updated 2026-07-24 with prompting-claude-opus-5.md + the Claude Opus 5 System Card); previously effort-level-decision-framework-claude-code-opus-4-7-sonnet-4-6.md. Critical for any session that uses Claude Code as of July 2026.

This file's name is deliberately model-agnostic: at each model release, update the Current lineup section and the tier tables — never the filename. (The pre-v1.7.0 name was opus-4-7-defaults.html; renaming it at every release was the debt this layout retires.)

# Current lineup (versioned)

Lineup as of 2026-07-24 (Claude Opus 5 release):

Model API id Claude Code alias Role in this doctrine Availability
Claude Sonnet 5 claude-sonnet-5 sonnet Workhorse default at high — most coding, most agentic work GA
Claude Opus 5 claude-opus-5 † opus Hardest multi-file refactor, debugging, architecture, pure reasoning; long-horizon agentic and 1M-context work. xhigh is where an Opus 5 coding run starts, not its ceiling. Thinking on by default (disableable only at effort high or below); 1M context as both default and maximum. GA
Claude Opus 4.8 claude-opus-4-8 — Prior flagship; stable reference baseline; the named fallback target for Fable 5 refusals. Opus 5's own safety classifiers fall back to it mid-run on ~5% of API calls (4% of trials) on agentic terminal tasks (Opus 5 System Card, p.152) — account for it before debugging a prompt. GA

† Provenance: the claude-opus-5 API string is environment-verified, not pack-verified — the research pack lists Opus 5's model string as “—” and states explicitly that no literal appears in its sources. Pin it from your own deployment config, not from the pack. The sources also name no fallback model for Opus 5; nothing is invented here to fill that gap.

Fable 5 / Mythos 5 left this workflow on 2026-07-07, as its dated exception declared: included in Max 20x until that date, then API-billed and dropped. The row is retired rather than kept as a stale note — an expired dated exception resolves to its declared successor state or it starts lying.

The durable anchor is Sonnet 5 + Opus 5, with Opus 4.8 as the stable baseline behind them. Models with bounded availability get dated notes, never scaffolding: no send-to-user tooling, no refusal-fallback wiring, no multi-day-timeout guidance enters project templates on their account.

# The 3 + 1 heuristics

  1. Default to high on Sonnet 5 for Claude Code. xhigh is the ceiling for the hardest work, not the session default — Sonnet 5 high already carries what Sonnet 4.6 called max.
  2. Pick the model first, the effort second. Sonnet 5 first for coding and agentic work; escalate to Opus 5 when reasoning depth (not code volume) is the bottleneck. On Opus 5, xhigh is the recommended starting point for coding/agentic work, not the ceiling. Plan-then-build sessions: plan mode on the stronger model (opusplan-style alias where your Claude Code build exposes it).
  3. max is per-subproblem rescue, not session default. Evidence, not preference: on GDPval-AA, xhigh reaches ELO 1827 using 25% fewer output tokens than max's 1861 while still beating every other model; on AA-Briefcase, xhigh/high use 15%/33% fewer tokens than max and still lead (p.178).
  4. Effort names don't carry equal depth across model versions. Sonnet 5 medium ≈ Sonnet 4.6 high; Sonnet 5 high ≈ Sonnet 4.6 max. Benchmark by observed thinking length, never by the level's name.

# Default tier per task

MOST CODING (features, refactors, tests-with-logic, reviews)
└─ Sonnet 5 + high ─────────────── the workhorse; near-Opus at Sonnet pricing

HARDEST MULTI-FILE REFACTOR / DEBUG / ARCHITECTURE
└─ Sonnet 5 + xhigh (cheaper first step) or Opus 5 + xhigh

HARDEST PURE REASONING / AMBIGUOUS DESIGN
└─ Opus 5 + xhigh ──────────────── xhigh is the START of an Opus 5 run

LONG-HORIZON AGENTIC / 1M-CONTEXT WORK
└─ Opus 5 ──────────────────────── consistent across the full window

UNTRUSTED CONTENT (web pages, PR diffs, third-party tool output)
└─ not a tier decision ─────────── least privilege + human gate; see § security surface

TESTS / DOCS / UTILITY SCRIPTS
└─ Sonnet 5 + medium ───────────── ≈ old Sonnet 4.6 high; rarely limiting

CLASSIFICATION / FORMATTING / SIMPLE RENAMES
└─ Sonnet 5 + low ──────────────── strictly scoped; raise effort if shallow

STUCK PROBLEM (one turn)
└─ /effort max for ONE turn ────── then drop back; max ≠ session default

# Effort recalibration across model versions

Effort levels are model-relative. Reusing yesterday's level names on today's models silently changes both cost and depth.

Sonnet 5 level ≈ Sonnet 4.6 equivalent Consequence
medium high Yesterday's "high" workloads now run fine at medium — free cost cut
high max A session pinned to xhigh out of habit pays old-max prices on every turn
  • Benchmark by observed thinking length, not the level name. The names are UI labels; the depth behind them moves at each release.
  • Sonnet 5 respects low strictly. At low/medium it scopes work to exactly what was asked. Good for latency and cost — but a documented under-thinking risk when a nominally mechanical task turns moderately complex. The fix is raising effort, never prompting around shallow reasoning.
  • Session default = high. xhigh is reserved for the hardest coding/agentic work; max is a one-turn rescue.

Opus 5 — sweep, don't carry over

  • Effort sets how much the model thinks, not how much it says. Lowering effort can reduce thinking volume without reliably shortening the visible response. To control response length, prompt for it explicitly — see behavior deltas.
  • low/medium produce strong quality at a fraction of the tokens and latency, and beat the same settings on prior Opus models. Use them wherever your evals show quality holds.
  • Re-run an effort sweep; do not reuse Opus 4.8 defaults. The numbers refuse to line up with intuition: FrontierCode's best score (53.4 main / 63.6 extended) is reached at medium, not xhigh/max (p.150–151). FrontierBench: xhigh 44.4% (best), high 39% for 19% fewer output tokens, low 25% for 64% fewer (p.152). AutomationBench: medium scores 24% at $0.89/task, outperforming prior Claude models at less than half the cost of comparable configurations (p.180).
  • Counter-signal, same weight — the sweep runs in both directions. Pilot feedback reports "overthinking": the model performs worse at higher effort on some tasks, and descends into self-correction loops that re-verify already-verified answers, especially at higher effort (p.82, p.81). Higher is not monotonically better.

# Opus 5 behavior deltas (verbosity, narration, scope, delegation)

Opus 5 performs well out of the box on existing Opus 4.8 prompts — this is not a rewrite-everything migration. Four behaviors typically need new constraint prompting. Each snippet belongs in the system/agent prompt of the surface where the behavior is actually observed — not in CLAUDE.md. Standing context pays for every line of every session (canon #1, #3); only the two lines that earn it live in the skeleton block below.

1 · Conversational verbosity. Default user-facing responses run longer than prior Opus models'. Effort will not fix it; ask for length:

Keep responses focused, brief, and concise. Keep disclaimers and caveats short, and spend most of the response on the main answer. When asked to explain something, give a high-level summary unless an in-depth explanation is specifically requested.

In a long system prompt, pair it with a short reminder near the end:

<tone_preference>
Keep outputs reasonably concise.
</tone_preference>

2 · Agentic narration cadence. Opus 5 announces what it is about to do and its per-message output in agentic sessions runs longer. Describe the cadence you want rather than what to avoid — positive examples of the communication style land better than prohibitions:

Before your first tool call, say in one sentence what you're about to do. While working, give a brief update only when you find something important or change direction. When you finish, lead with the outcome: your first sentence should answer "what happened" or "what did you find," with supporting detail after it for readers who want it.

3 · Written deliverable length. Separate from conversational verbosity: files Opus 5 writes to disk (reports, plans, summaries) are often longer than on prior models. Any surface that authors documents needs explicit calibration:

Match the length of written documents to what the task needs: cover the substance, but do not pad with filler sections, redundant summaries, or boilerplate.

4 · Task scope. Opus 5 can expand a task on its own — adding steps nobody requested, applying its own judgment about what the task should be. "Poor calibration of task scope" is named in the system card: it proactively finds real edge cases but also over-engineers and over-emphasizes marginal changes (p.26). For narrow tasks, constrain scope:

Deliver what was asked, at the scope intended. Make routine judgment calls yourself, and check in only when different readings of the request would lead to materially different work. If the request seems mistaken or a better approach exists, say so in a sentence and continue with the task as asked rather than quietly narrowing, widening, or transforming it. Finish the whole task, and stop short of actions that are clearly beyond what was asked.

5 · Delegation. Opus 5 delegates more readily than prior models. Delegation pays on genuinely independent, sizeable tracks — BrowseComp: a 10-agent team reaches 93.6% (+3.1pp over best single-agent) with a 5.6–5.9× latency speedup; ProgramBench: a 5-agent team gets 2.2× latency improvement at equal score (p.164, p.166). Small or non-parallelizable work does not clear that bar:

Delegate to a subagent only for large tasks that are genuinely independent and parallelizable, such as a wide multi-file investigation. Do not delegate work you can finish yourself in a handful of tool calls, and do not use subagents to verify or double-check your own work. If one subagent can complete the task, use one rather than several, and keep spawn counts low.

6 · Self-correction and correction narration. Opus 5 catches and fixes its own mistakes without prompting — instructing re-checks it already performs compounds with its own behavior and adds cost without improving results (see anti-patterns). It also narrates corrections more than prior models; pilot feedback flagged fabricated data followed by "theatrical retractions", over-dramatic phrasing and unprompted apologies for prior turns (p.81). To bound it:

Only correct an earlier statement when the error would change the user's code, conclusions, or decisions. State corrections plainly and briefly, then continue the task. For slips that change nothing for the user, make the fix and move on without noting it.

# Running with thinking disabled

Opus 5 runs with thinking on by default, and thinking can be disabled only at effort high or below. With thinking off, two artifacts can appear in visible output:

  • Tool calls as text. The model occasionally writes a tool call into its user-facing text instead of emitting a structured tool_use block. The turn completes normally and the call never runs — and in agentic loops the leaked text stays in conversation history, so later turns are affected too. Most common on tool-heavy workloads such as search.
  • Internal XML tags in output. The model can emit <thinking> or other internal tags into its visible response.

The primary mitigation for both is to keep thinking enabled and control token cost with lower effort instead of disabling thinking. Two traps if you must run with it off: a system-prompt rule instructing the model not to think or not to reason increases tag leakage — remove it; and an instruction that names <thinking> specifically is less effective than the general form. Where an explicit instruction is wanted:

You may say a brief sentence before using a tool.

Do not include internal or system XML tags in your response.

# Model choice by security surface

Two System Cards measure prompt-injection resistance on different benchmarks. They are reported separately below, each with its own comparison set. Their percentages are not comparable to each other, and merging them into one ranking would fabricate a comparison neither source makes.

  • Benchmark 1 — Sonnet 5 System Card (coding-environment and browser-use prompt-injection attack success). Coding environment: 0.31% on Sonnet 5 (with thinking) vs 7.03% on Opus 4.8 (p.62–65). Browser use: 0.93% on Sonnet 5 vs 31.5% on Opus 4.8 and 50.7% on Sonnet 4.6 (p.63). Comparison set: Sonnet 5, Opus 4.8, Sonnet 4.6 — Opus 5 was not measured here.
  • Benchmark 2 — Opus 5 System Card (Gray Swan Indirect Prompt Injection; probability an attacker succeeds within 15 attempts). Opus 5 2.0%, Mythos 5 2.6%, Opus 4.8 5.5%, Sonnet 5 5.9%, best non-Claude model 16.5%. Within 1 attempt: 0.5% (Opus 4.8) → 0.2% (Opus 5). Opus 5 is described as the most robust model tested (p.72–73). Comparison set includes both Sonnet 5 and Opus 5.

What changed for doctrine is narrow and specific: the rule "prefer Sonnet 5 on untrusted surfaces" was anchored on a comparison against Opus 4.8, and that baseline is retired. On the one benchmark where Opus 5 and Sonnet 5 were measured together, Opus 5 is the more injection-robust of the two. Untrusted content is no longer a model-tier decision.

What the section teaches instead:

  • No current tier is at zero. The control is architecture, not tier: least privilege on tools, no secrets in an agent's context, and a deterministic human gate on anything irreversible.
  • Layer defenses the model does not provide. Anthropic's own production agentic products run probes that inspect tool results before the model acts on them, and "auto mode" additionally pairs probes with a classifier that can block dangerous tool calls outright — two independent layers an attack must defeat (p.72). A project consuming untrusted content should ask which of those two layers it has, not which model it picked.
  • Corollary, unchanged — over-refusal on security-shaped prompts: Sonnet 5 refuses more legitimate dual-use security work than Sonnet 4.6 (91.55% success on benign dual-use tasks vs 97.33%). Security-adjacent prompts (pentest tooling, recon scripts, auth hardening) need explicit authorization framing — state the engagement, the ownership of the target, and the defensive intent in the prompt itself.

# Per-subagent effort frontmatter

Subagents do NOT inherit session effort by default — set explicitly in frontmatter:

---
name: lint-fix
model: sonnet
effort: low
---
Subagent role Effort
Mechanical (lint-fix, git-publisher, CLI caller) low
Bulk implementer (per-task TDD-light) medium
Reviewer / researcher high
Planner / architect xhigh

On Sonnet 5 these named levels each carry roughly one tier more depth than they did on Sonnet 4.6 (see recalibration). Keep the role→level mapping, but watch low agents: Sonnet 5's strict scoping means a "mechanical" agent whose task quietly grows complex under-thinks silently — recalibrate by observed thinking, not tradition.

On Opus 5 the same table is a starting point, not a measurement. The sources direct you to sweep on your own evals, and this table is not one — so no blind re-baseline is applied here. Two observable signals justify moving an agent a level: an xhigh agent that visibly loops on self-correction and re-verifies already-verified answers (p.81, p.82 — the model can perform worse at higher effort) → drop a level; a low/medium agent that silently under-scopes → raise one.

# In-session diagnostic matrix

When something feels off, diagnose before raising effort:

Signal Diagnosis Action
Spec ambiguous Need plan first Switch to plan mode on the stronger model
Solution too shallow Underpowered Bump effort one level (on Sonnet 5, never prompt around shallow reasoning)
Solution overengineered Overpowered Drop one level
Long sessions getting expensive Later-turn thinking grows at high+ effort /clear more often or drop one effort level
Subagent under-tools Low effort / thinking-off reduces tool reach on Sonnet 5 Add positive prompt example + raise effort, not "MUST use X"
Reviewer reports trivial issues Defensive scaffolding in prompt Rewrite prompt: explicit AC + scope + severity matrix
Reviewer reports too FEW findings Severity-filter language obeyed literally (recall trap) Coverage-not-filtering: report everything with confidence + severity; filter downstream
Failing repeatedly Probably underpowered One-turn /effort max, then drop back; switch model on second failure
Code subtly wrong but spec satisfied Under-thinking on multi-step work at low/medium Bump to high or xhigh
Response is long, effort already low Effort controls thinking, not saying Prompt for length explicitly (behavior deltas) — don't drop effort further
Model built a verification pipeline and spent its budget on it Unproductive self-verification (p.26) Remove verification instructions from the prompt and the harness; keep the deterministic gates
Deliverables came back padded (extra sections, redundant summaries) Written-deliverable length grew vs prior models Add the length-calibration snippet to the authoring prompt
More subagents than the work has independent tracks Delegates more readily than prior models Cap delegation (behavior deltas); one subagent when one suffices
Task grew steps nobody asked for Poor calibration of task scope (p.26) Task-scope-constraint snippet
Long autonomous terminal run produced inconsistent output Safety classifiers flagged/refused ~5% of API calls (4% of trials) with fallback to Opus 4.8 mid-run (p.152) Check for the fallback before debugging the prompt

# Anti-patterns (Claude 4.7+ / Claude 5 family)

  • Defaulting a long session to max — ~2x the spend for ~3-4 percentage points of quality.
  • Pinning xhigh out of habit — on Sonnet 5, high already carries old-max depth; xhigh-by-default pays a premium the task rarely needs.
  • Adding prompt scaffolding to compensate for shallow reasoning → "raise effort, not scaffolding."
  • Migrating old prompts unchanged — severity-filter language ("don't nitpick", "only critical issues") is obeyed literally and you lose review recall. See the coverage-not-filtering row in anti-pattern-catalog.html.
  • Letting mechanical subagents inherit session effort → set effort: explicitly in their frontmatter.
  • Trusting low on moderately complex work — Sonnet 5 scopes strictly; the failure is silent (literal spec satisfied, downstream broken).
  • Setting thinking: {budget_tokens: N} — returns 400 on all current models (Opus 4.7 through Opus 5, Sonnet 5). Adaptive thinking + effort is the only mode.
  • Lowering effort to shorten a reply — effort sets thinking, not response length. Ask for the length you want.
  • Disabling thinking to cut cost on Opus 5 — leaked tool-calls-as-text persist in agentic history and poison later turns. Lower the effort instead; see thinking disabled.
  • A system-prompt rule telling the model not to think or not to reason — it increases internal-tag leakage rather than preventing it.
  • Naming <thinking> specifically in a suppression instruction — measurably less effective than the general "no internal or system XML tags" form.
  • Telling the model to double-check or re-verify its own output — Opus 5 already does; the instruction triggers documented unproductive self-verification, including self-built verification pipelines that consume the time budget before results land (p.26). Deterministic gates and independent review are a different thing and stay.
  • Uncapped delegation on small work — Opus 5 delegates readily; the payoff threshold is genuinely independent, sizeable tracks (p.164, p.166), not work you can finish in a handful of tool calls.
  • Setting non-default temperature/top_p/top_k on Sonnet 5 — returns 400. Steer tone/variety via system-prompt instructions instead.
  • Prefilling the last assistant turn — removed since Claude 4.6 (400). Move the constraint into the system/user turn or use structured outputs.

# Effort precedence

ENV var ($CLAUDE_CODE_EFFORT_LEVEL)
    ↓
Skill or subagent frontmatter (effort: ...)
    ↓
Session-level /effort
    ↓
settings.json effortLevel
    ↓
Model default

On Opus 5, high is also the highest effort at which thinking can be disabled — above it, thinking is always on.

To pin an effort level permanently for a machine, set in ~/.claude/settings.json:

{"effortLevel": "high"}

high is the recommended pin on the current lineup; reserve xhigh for per-session or per-subagent escalation.

# Non-Claude-Code deployments

Model aliases (opus, sonnet) auto-resolve only in Claude Code. On Bedrock / Vertex / Foundry and in direct API code, pin explicit model strings (claude-sonnet-5, claude-opus-5 †) and confirm per-deployment config. † The Opus 5 string is environment-verified, not pack-verified — see the lineup note; take it from your own deployment config.

# When xhigh pays for itself

xhigh pays back when retries are expensive — xhigh's 2× token cost is lower than high's 1.25× expected runs × debugging overhead for tasks where:

  • Acceptance criteria are partially ambiguous
  • Multiple files need to coordinate
  • Edge cases matter (state machines, transactions, refunds)
  • Migration risk is real

xhigh does NOT pay when:

  • Task is mechanical / unambiguous
  • Concurrent Max-plan sessions where weekly quota constrains you
  • You're already inside Plan Mode (the model already concentrates effort there; max is the trap)
  • Sonnet 5 at high already delivers old-max depth — verify the task actually outruns it before escalating
  • You're reaching past xhigh to max on Opus 5 — GDPval-AA xhigh reaches ELO 1827 using 25% fewer output tokens than max's 1861, while still beating every other model (p.178)

# CLAUDE.md skeleton block (BOOTSTRAP injects)

## Default model + effort
- Default: sonnet (Sonnet 5) at high — workhorse for most coding; near-Opus quality at Sonnet pricing, gentler on quota.
- Escalate: opus (Opus 5) at xhigh for the hardest multi-file refactor, debugging, architecture and pure reasoning; sonnet (Sonnet 5) at xhigh is the cheaper first step. On Opus 5, xhigh is where a coding run starts, not max.
- Effort sets how much the model thinks, not how much it says — ask for the length you want instead of lowering effort.
- Opus 5 verifies and self-corrects on its own — asking it to check its own output again just burns budget.
- Independent review is a different job and it stays: a reviewer reads a diff it didn't write, against the spec.
- Opus 5 widens scope on its own — state the scope you want and the boundary you don't want crossed.
- Delegate only genuinely independent, sizeable tracks; when you do fan out, dispatch them in one message. Work you can finish in a handful of tool calls stays inline.
- Untrusted content (web pages, PR diffs, third-party tool output): no tier is injection-proof — least privilege on tools, and a human gate on anything irreversible.
- Plan then build: plan mode on the stronger model (`opusplan`-style alias where available).
- Drop: `/effort low` for classification, formatting, simple renames. Sonnet 5 respects low strictly — raise effort if reasoning turns shallow; don't prompt around it.
- Rescue: `/effort max` for ONE turn on stuck problems, then drop back.
- Effort names don't carry equal depth across model versions (Sonnet 5 medium ≈ Sonnet 4.6 high; high ≈ old max) — benchmark by observed thinking length.
- Subagents declare their own effort. Mechanical → low. Implementer → medium. Reviewer → high. Planner → xhigh.
- State explicit intent, constraints, acceptance criteria, file paths. Don't generalize silently.

This block is the user's contract with the current lineup (Sonnet 5 + Opus 5). meta-govern ensures it appears in every project's CLAUDE.md — the identical text lives in templates/CLAUDE.md.tpl, and four-tier-architecture.html carries a compressed one-liner of it; the three surfaces stay in lockstep.
